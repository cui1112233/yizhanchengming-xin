# 小说获取与批量工厂实用性修复设计

## 目标

修复审查中确认的四个直接影响使用的问题：小说获取并发配置不生效、开始处理请求可能等待抓取、分类未完成时两个页面提示与真实门槛不一致，以及处理页重复的解析预览入口和批量工厂首页刷新不足。

## 范围

- 保留原文、处理正文、分类、改写、提交的独立阶段状态。
- 不改变上游原文接口协议。
- 不在测试或本地验证中触发真实抓取、付费 AI 调用或外部提交。
- 不清理工作区中与本任务无关的已有修改。

## 设计

### 1. 并发配置

小说获取工作器继续按书籍拆分任务，并以账号配置中的 `fetch.concurrency` 创建有界并发。配置读取失败时使用明确的默认值，配置值限制在现有安全上限内。测试必须证明配置为 3 时至少有两个上游请求同时进行，并且单书失败不会阻塞其他书。

### 2. 开始处理与后台执行

`process/start` 只负责解析输入、保存任务与审计记录、原子入队并返回 `202 Accepted`。原文抓取、原文落库、规则处理、敏感词、分类和改写全部由队列工作器执行。开始接口不得等待上游请求完成；测试使用会阻塞的上游假服务验证响应先返回、后台任务随后继续。

### 3. 分类门槛与页面表达

抓取成功、分类完成、改写可执行分别保留独立状态。分类未确认时，两个页面都显示“已抓取，等待分类确认”，并禁止自动改写消耗模型额度；分类确认后可从分类阶段继续，不重新抓取原文。批量工厂不再显示“分类失败不影响生产”这类与实际改写门槛冲突的提示。

### 4. 页面流程与刷新

处理页移除重复的“解析预览”操作入口，输入格式校验和识别结果仍在提交前完成。批量工厂首页在可见状态下进行低频刷新，页面隐藏时暂停；手动刷新继续保留。刷新失败保留上一次列表并显示可重试错误，不清空已显示批次。

## 错误与恢复

- 抓取失败只进入抓取重试，不丢失已保存的原文。
- 处理失败只进入处理重试，不重新抓取已经落库的原文。
- 分类失败进入等待分类，不误报为抓取失败。
- 页面刷新或切换不会覆盖较新的批次或任务状态。

## 验证

- 后端：小说获取工作器并发、后台返回、分类门槛和重试状态测试。
- 前端：解析入口、分类提示、批量工厂首页刷新和错误保留测试。
- 运行 `git diff --check`、聚焦 Go/Node 测试和前端生产构建。
- 不做真实上游抓取、AI 调用、提交、部署或服务重启作为测试步骤。
