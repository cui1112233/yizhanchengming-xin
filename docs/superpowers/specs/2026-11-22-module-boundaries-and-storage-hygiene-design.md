# V88 功能模块解耦与磁盘治理设计

日期：2026-11-22  
维护分支：`v88`

## 1. 目标

本次工作同时解决两个长期问题：

1. 构建、发布和配置快照持续累积，最终阻断视频合成等需要写入大文件的任务。
2. 页面入口、HTTP 接口、任务流程和数据读写混在公共大目录中，一个功能改动容易影响其他功能。

最终规则是：**只有基础 service 能被多个功能模块共用；功能模块的页面、接口、任务、状态和数据访问必须各自封闭。**

## 2. 已确认现状

### 2.1 磁盘

- 线上根盘 20GB，排查时使用率为 82%；此前达到 87.3% 时，媒体写入保护已经阻止新视频合成。
- `/opt/www/yzcm-ui/releases` 有 20 份旧前端发布目录，约 3.1GB；当前 Go 服务、Nginx 和 systemd 均未引用这些目录。
- `/opt/www/new-api/backups` 约 1.2GB，但 `new-api.service` 仍在运行，因此不纳入本轮直接清理。
- MySQL 表 `batch_factory_v12_config_snapshots` 约 1.44GB，是数据库最大的单表，不能当普通缓存直接删除。
- 本地 `executors/doubao-relay/target` 约 7.34GB，属于可重新生成的 Rust 编译缓存。
- 本地 `backend/` 根目录累计二十多个未纳入 Git 的旧 Go 可执行文件，合计接近 4GB。
- 本地 `.release` 约 6.36GB，并登记了大量历史 detached worktree。

### 2.2 代码耦合

- `backend/internal/httpapi` 有 585 个 Go 文件，批量工厂、小说获取、AI-CUT、Agent 等入口混放。
- `shuihuo_projects.go` 约 241KB，`batch_factory_automation.go` 约 230KB。
- `BatchFactoryNovelList.jsx` 约 454KB。
- 多个 HTTP 入口同时直接依赖 `batchfactoryv11`、`novelfetchworkshop`、`prompt` 和视频管理连接器。

## 3. 方案比较

### 方案 A：只整理文件，不改变依赖

优点是改动小；缺点是大文件和跨模块调用仍然存在，很快会再次混乱。不采用。

### 方案 B：一次性移动全部目录

目录会立刻变整齐，但数百个 Go 文件和前端引用同时变化，回归风险过高，也很难判断哪个移动造成故障。不采用。

### 方案 C：建立边界后逐模块迁移（采用）

先建立公共 service 接口和模块注册入口，再按照“小说获取 → 批量工厂 → 漫画 → AI-CUT → Agent”的顺序迁移。每次只迁一个完整功能闭环，并保留行为测试证明对外接口没有变化。

## 4. 目标目录

遵守项目长期约定，最终目录按职责划分：

```text
api/
  cmd/                       Go 程序入口
  modules/
    novel-fetch/             小说获取：接口、任务、状态、数据访问
    batch-factory/           批量工厂：视频和自动生产
    comic/                   漫画生产与漫画发布
    aicut/                   AI-CUT
    agent/                   Agent 与画布
    video-management/        视频管理系统业务适配
  service/                   唯一允许跨模块共用的能力
    textmodel/
    imagemodel/
    videomodel/
    tts/
    storage/
    queue/
    media/
    auth/
  prompt/                    后端系统提示词
  platform/                  MySQL、Redis、HTTP、日志、配置等底座

前台/
  src/modules/
    novel-fetch/
    batch-factory/
    comic/
    aicut/
    agent/
  src/service/               API 客户端、认证、上传等公共调用
  src/shell/                 路由、导航、主题和应用外壳

后台/
  src/modules/               管理端功能模块
  src/service/               管理端公共 API 能力
  src/shell/                 管理端应用外壳
```

迁移期间现有 `backend/`、`frontend/` 仍作为可运行入口；只有当一个模块的源码、测试、构建脚本和 Go embed 全部迁完后，才删除对应旧入口。禁止通过复制形成两份长期源码。

## 5. 依赖规则

1. 模块只能依赖 `service`、`prompt`、`platform` 和自身目录。
2. 模块不能导入另一个模块的内部包。
3. 跨模块协作只能通过小接口、事件或明确的数据合同完成。
4. HTTP 路由由每个模块自己的 `RegisterRoutes` 注册；总路由只负责装配。
5. 前端模块不能从另一个页面目录深层导入组件或状态。
6. 系统提示词只存在于后端 `prompt`，前端只接收后端返回的最终结果。
7. MySQL 表可以共库，但每张表必须有明确归属模块；跨模块读取必须通过归属模块提供的 service 接口。

## 6. 第一阶段迁移范围

第一阶段选择“小说获取”作为样板：

- 把小说获取的 HTTP 路由、请求结构、任务编排和数据访问收进独立模块。
- 把文本模型、存储、队列和认证保留为共享 service。
- 前端把 `NovelFetchPage.jsx` 拆成模块入口、列表、详情、设置和状态组件。
- 保持现有 URL、接口 JSON、数据库表和用户可见文字不变。
- 增加依赖边界检查，防止新代码重新导入其他模块内部文件。

样板通过后，再按相同结构迁移批量工厂；批量工厂内部再分视频生产和漫画生产两个子模块。

## 7. 磁盘治理

### 7.1 本地

- Rust `target/`、历史 Go 可执行文件和旧构建目录视为可再生成产物。
- 只保留当前 `qiantie-local.exe` 和一份 `qiantie-local.previous.exe`。
- release worktree 在确认无未提交修改、提交已在 Git 中可达后再移除。
- 临时截图、日志和一次性检查文件归档到 `_local-archive-20261028/`，不再散落根目录。

### 7.2 线上

- Go 程序只保留“当前版本 + 一个已验证回滚版本”。
- 旧前端发布目录只保留最新一份审计证据；Go embed 生效后不再重复保存整套前端发布目录。
- `new-api` 按独立服务处理，本轮不跨服务删除其备份。
- 配置快照采用“按批次保留最近版本 + 发布/失败关键版本长期保留”的策略，必须先写迁移和审计脚本，再分批删除。
- 媒体文件优先存 TOS；本地只保存近期播放副本，并设置容量阈值和过期清理。

## 8. 安全阈值与自动治理

- 根盘低于 75%：正常。
- 75% 至 82%：记录告警并执行可再生成缓存清理。
- 82% 至 88%：暂停非必要构建，但允许已有媒体任务完成。
- 高于 88%：阻止新的大文件任务，并在界面明确显示具体占用来源。
- 发布脚本完成后自动只保留一个回滚程序，并清理本次临时构建目录。
- 每日生成磁盘报告，分别列出程序、数据库、媒体、日志和其他服务，禁止只显示一个总百分比。

## 9. 验收标准

### 磁盘

- 本地删除的内容全部是可重新生成产物，源码和运行数据不受影响。
- 线上当前服务、最新回滚、业务数据库和用户素材保留。
- 清理后线上根盘使用率低于 70%，并能成功执行一次真实媒体写入。

### 模块化

- 总路由不再包含具体业务处理。
- 第一阶段模块没有直接导入其他业务模块内部包。
- 原有接口、页面路径和数据库数据兼容。
- Go 测试、前端测试、构建、Go embed、本地 4001 和线上运行依次通过。

## 10. 回退

- 文件迁移按小提交进行，每次只迁一个模块闭环。
- 数据库清理由独立审计 SQL 先导出待删 ID 和统计，再执行删除。
- 线上始终保留一个已验证回滚二进制。
- 任何阶段验证失败，只回退当前阶段，不恢复已经退役的 Node 发布链。
