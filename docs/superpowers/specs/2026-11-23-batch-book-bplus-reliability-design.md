# 批量测书 B+ 稳定性修复设计

日期：2026-11-23  
状态：已由用户批准设计方向，等待书面规范复核

## 1. 目标

本次修复针对 `/novel-fetch` 批量测书完整链路，解决以下已经由线上只读数据和参考源码对比确认的问题：

1. 明确不可恢复的 121 业务错误被持续自动重试。
2. Redis 执行租约与队列等待时间共用同一个短时长，长任务可能在仍然运行时被当成孤儿重新派发。
3. 历史任务存在重复运行、终态残留重试标记、悬空批次和无引用正文。
4. 生成完成、上传完成和上传结果不明必须严格区分。
5. 重试只能补做缺失阶段和缺失版本，不能覆盖已成功结果。

目标不是重写批量测书，也不改变 Batch Factory、漫画或视频生产链路。现有 Go、MySQL、Redis、TOS 架构保持不变。

## 3. 参考源码对比结论

参考文件：`批量原文改文系统_源码_20261015_181412.zip`。

### 3.1 吸收的规则

- 上传必须按书和版本保存确认凭证。
- 请求已经发出但结果不确定时，先进入待核对状态，不能盲目重传。
- 重试只处理失败或缺失阶段，不覆盖成功版本。
- 活跃工作线程超过预计时长时继续持有并刷新租约，不重复派发。
- 定时取消只删除该定时真正创建的任务。
- 启动恢复需要检查孤儿执行状态、上传中断状态和旧状态兼容。
- 删除、重试和上传必须保持用户选择范围与账号隔离。

### 3.2 不吸收的实现

- 参考源码的原文失败次数没有最终上限，不能照搬。
- 参考源码使用本地 JSON 文件和文件锁；本项目继续使用 MySQL 和 Redis。
- 参考源码默认关闭自动清理；本项目保留安全延迟回收机制。
- 双进程文件锁不能代替 Redis 分布式租约。

## 4. 组件边界

### 4.1 上游错误分类器

在 Go 后端的批量测书上游模块中增加结构化错误，至少包含：

- 错误阶段；
- HTTP 状态码；
- 121 业务码；
- 可读原因；
- 是否允许自动重试；
- 建议动作。

上层调度只读取结构化结论，不再通过中文错误文字猜测是否重试。

错误处理表：

| 错误类型 | 自动处理 |
| --- | --- |
| 缺少书号、平台无效、书不存在、章节不存在、明确的 121 业务 400 | 第一次失败立即转人工 |
| 401、403、账号或配置无效 | 转等待配置或人工处理 |
| 408、429、连接失败、超时、502、503、504 | 允许退避重试，最多 5 次 |
| 2xx 但返回损坏 JSON、错误页面或临时空响应 | 作为临时上游错误有限重试 |
| 未分类错误 | 有界重试，达到上限后转人工 |

临时错误沿用现有可配置策略，但默认退避时间固定为 1、5、15、30、60 分钟，共 5 次。收到合法的 `Retry-After` 时取配置退避与服务端建议中的较大值。明确业务错误不消耗这 5 次预算，直接转人工。

转人工时必须写入 `manualOnly`、明确的人工原因和最后一次错误，并清除下一次自动重试时间。

### 4.2 Redis 执行租约

队列领取等待时间与执行租约彻底分开：

- 领取等待时间只控制消费者等待新任务多久；
- 领取等待默认 30 秒，执行租约默认 10 分钟，两者使用不同配置；
- 每次领取生成唯一租约令牌；
- 工人执行期间每 30 秒续租一次；
- 续租、完成、失败和回收都必须比较租约令牌；
- 只有租约确实失效且当前工人不再拥有任务时，才能回收孤儿任务。

如果工人失去租约，必须取消后续写入和上传，避免旧工人覆盖新任务结果。耗时模型请求返回后，在保存正文前再次检查租约所有权。

### 4.3 任务状态裁决

任务对外状态继续由后端统一裁决，页面不得自行拼接多个状态字段。

- 生成模式：原文完成且所有选中 AI 版本均有有效正文，即可完成。
- 自动上传模式：除生成条件外，所有选中版本都必须存在已验证的远端提交凭证，才能完成。
- 请求已发送但没有可靠回执：状态为待核对，不得视为失败，也不得直接重传。
- 完成、停止、取消、人工处理等非自动状态必须清除自动重试时间和活动队列标记。
- 已完成版本是权威结果，调整目标数量或重试时只补缺失版本。

### 4.4 上传凭证和防重复

每个书号、版本的提交记录至少保存：

- 本地正文内容哈希；
- 本次提交开始时间；
- 请求是否实际发出；
- 远端提交编号；
- 远端读取到的记录；
- 是否已验证；
- 最终状态与失败原因。

规则如下：

1. 已验证成功且正文哈希不变时，普通重试跳过该版本。
2. 请求未发出即可安全重试。
3. 请求已发出但无确认时先远端核对。
4. 远端明确不存在本次提交后，才允许安全重传。
5. 用户显式要求覆盖时才允许强制再次上传，并留下覆盖审计记录。

### 4.5 定时任务与选择范围

- 定时记录分别保存请求书号、实际创建书号、重复跳过书号和已派发书号。
- 取消未执行定时时，只删除该定时实际创建且仍归属于该定时的任务。
- 已存在任务、其他账号任务和其他定时任务不得被连带删除。
- “重试选中”只能处理前端提交的选中 ID，不得扩大到全批次。
- 一个忙碌书号不能阻塞同批次其他空闲书号派发。

### 4.6 正文生命周期与一致性诊断

新增只读一致性诊断和安全标记流程：

- 文档引用正文但正文不存在：报告为存储缺失，不自动伪造完成。
- 正文不存在对应文档：最后更新时间超过 7 天后标记为 `releasable`。
- 正文存在对应文档但不在 `bodyRefs` 中：最后更新时间超过 7 天后标记为 `releasable`。
- 标记后继续遵守正文保留天数，到期才删除 MySQL 记录和 TOS 对象。
- 备份表不参与自动扫描和自动清理。
- 当前批次指向不存在任务时，报告悬空配置；只有确认没有活动队列和定时任务后才允许清除。

诊断接口使用 `/api/novel-fetch-workshop/diagnostics`。普通用户只能看到自己的汇总；管理员只能通过现有鉴权查看跨账号汇总。接口只返回数量、状态和脱敏标识，不返回正文、密钥、密码或完整账号名。

## 5. 数据流

正常处理链路：

1. 解析输入并保存任务快照。
2. 获取结构化分类结果；缺失且允许时只自动分类一次。
3. 调用 121 获取原文。
4. 上游错误分类器决定立即转人工或有限重试。
5. 保存原始正文和处理后正文引用。
6. 按选中版本生成缺失 AI 正文；每次保存前检查租约。
7. 生成模式在版本齐全后完成。
8. 自动上传模式为缺失版本建立提交计划。
9. 按版本保存请求事实和远端确认凭证。
10. 所有目标版本确认后完成；不确定结果进入待核对。

重启恢复链路：

1. 扫描 Redis `processing` 列表。
2. 有匹配活动租约的任务保持不变。
3. 无活动租约的任务与 MySQL 状态交叉核对。
4. 确认是孤儿后释放旧锁并转入有界重试。
5. 已完成、已停止、已取消和人工保持任务不得重新入队。

## 6. 数据兼容与迁移

- 不修改或删除 `*_bak_testreset_20261121` 备份表。
- 不恢复历史任务。
- 新增字段优先放入现有文档元数据或运行审计结构；需要数据库结构时使用可重复执行的 MySQL 迁移。
- 当前正式表为空，因此迁移重点是保证以后新任务正确写入，而不是批量改写历史正文。
- 对悬空当前批次只先报告，不在部署时自动清除。

## 7. 测试要求

### 7.1 上游错误测试

- 121 明确业务 400 第一次失败即转人工。
- 401、403 转等待配置或人工处理。
- 429、超时和 503按退避策略重试，最多 5 次。
- 成功后清除原文阶段重试记录。
- 人工重试可以显式解除人工保持，但不会自动解除。

### 7.2 队列与租约测试

- 领取等待超时不影响执行租约时长。
- 长任务持续续租时不得被孤儿回收器删除。
- 租约令牌不匹配时，旧工人不能续租、完成或失败任务。
- 工人失去租约后不得保存正文或开始上传。
- 同一本书不能同时拥有两个活动任务。
- 一个书冲突时，同批次其他书仍能派发。

### 7.3 上传与状态测试

- 已确认版本不会重复上传。
- 未发出请求的失败可以安全重试。
- 已发出但未知的结果必须先核对。
- 部分成功只补失败版本。
- 生成模式不因未开启上传而卡住。
- 自动上传模式没有全部确认时不能显示完成。
- 终态不能残留自动重试标记。

### 7.4 存储与删除测试

- 删除文档时正文先标记可回收，不立即删除。
- 无文档正文和无引用正文在宽限期后进入可回收。
- 备份表永远不被自动清理。
- 永久删除选中任务不能扩大为删除全部。
- 定时取消只删除 `created_ids` 所属任务。

### 7.5 验收范围

- 后端相关 Go 测试全部通过。
- 前端相关测试和构建通过。
- 本地 4001 的运行版本、健康接口和只读诊断符合预期。
- 测试使用假的上游、模型和上传器，不产生付费模型调用或真实上传。
- 推送后再部署线上，线上只进行健康检查和 MySQL、Redis 只读核对，不自动触发历史任务。

## 8. 发布顺序与回滚

顺序固定为：

1. 在当前 `v88` 主开发分支完成本地实现和测试。
2. 构建前端并通过 Go `embed` 打入单个后端二进制。
3. 启动并验证本地 4001。
4. 只提交本次相关文件，推送到远端主开发分支。
5. 备份线上当前二进制，部署新的单文件二进制。
6. 验证健康接口、运行版本、正式表数量、Redis 队列和诊断统计。
7. 若出现异常，恢复部署前二进制；不回滚数据库备份表，不恢复历史任务。

本项目禁止使用 GitHub Actions 部署。
