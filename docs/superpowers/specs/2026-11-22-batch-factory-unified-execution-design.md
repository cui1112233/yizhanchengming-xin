# 批量工厂统一执行内核设计

日期：2026-11-22
适用项目：V88 批量工厂
维护分支：`v88`

## 1. 背景

当前批量工厂已经具备正文读取、分类、提示词、资产、视频、漫画、合成、上传和发布等能力，但这些能力没有共享一个权威的任务状态。

现有页面需要同时拼接书籍字段、自动化任务、视频任务、合成任务和外部上传回执，因此出现过以下问题：

- “立即执行已选”只调用单个视频阶段，没有运行缺失的前置阶段。
- 视频批次误用活动中的漫画预设。
- 页面显示排队执行，但后端因已有任务直接返回冲突。
- 成片存在却没有上传，或上传已经接收却被提前显示为完成。
- 历史失败覆盖后来成功的结果。
- 服务重启、重复点击和自动调度同时发生时存在重复生成或重复上传风险。
- 一本书失败后占住批次，使其他书不能继续。
- 前端核心页面和后端自动化核心文件过大，修改局部行为容易影响整条链路。

本设计建立一套统一执行内核，使立即执行、定时执行、视频生产、漫画生产、合成、上传和外部回读共享同一套任务合同，同时保持视频与漫画的业务阶段互相隔离。

## 2. 已确认的产品规则

以下决定已经确认，不再作为实施阶段的开放问题：

1. 只有外部平台回读确认成功，一本书才允许显示“完成”。
2. 任务启动时冻结配置；运行过程中修改配置只影响下一次任务。
3. 一本书失败不阻塞其他书，批次继续执行。
4. 重复点击复用当前任务，只补齐缺失书籍和缺失阶段。
5. 上传结果不确定时先回读核对，确认不存在后才允许重传。
6. 已生成的视频、图片、音频和成片默认复用；只有用户明确选择强制重做才创建新版本。
7. 实施与交付顺序固定为：本地验证、推送 GitHub 远端、线上部署和真实验收。

## 3. 目标和非目标

### 3.1 目标

- 为批量工厂建立一个 MySQL 权威业务状态。
- 统一立即执行和定时执行入口。
- 让重复点击、并发请求、服务重启和队列重投保持幂等。
- 按错误类别决定重试、核对、停止或人工处理。
- 明确区分产物就绪、已提交、待确认和已完成。
- 复用已经成功的阶段，避免重复扣费和重复上传。
- 逐步拆分前后端大文件，并建立视频与漫画的明确边界。
- 保持旧任务、旧数据和现有页面路径兼容。

### 3.2 非目标

- 不一次性重写整个批量工厂。
- 不把 Redis 变成业务事实来源。
- 不在前端保存系统提示词正文。
- 不在第一阶段删除旧任务表或旧状态文件。
- 不把视频和漫画合并为同一套业务阶段。
- 不引入完整事件溯源系统。

## 4. 总体架构

```text
前端执行请求
    ↓
执行入口：确保这些书达到目标状态
    ↓
配置冻结：模型、预设、提示词版本、发布配置
    ↓
统一任务规划器
    ↓
单书执行内核
    ├─ 视频处理器
    │   正文 → 分类 → 资产 → 分镜提示词 → 视频 → 合成 → 上传 → 回读
    └─ 漫画处理器
        正文 → 分类 → 漫画资产 → 分页提示词 → 出图 → 合集 → 发布 → 回读
    ↓
统一状态投影
    ↓
前端展示后端权威状态
```

### 4.1 组件职责

- **执行入口**：接收批次、书籍范围、生产模式和目标状态，不接收具体下一阶段。
- **配置冻结器**：保存任务启动时的模型、预设、提示词版本、发布组织和运行参数。
- **任务规划器**：读取已有产物和状态，计算每本书真正缺失的阶段。
- **单书执行内核**：负责排队、并发、恢复、暂停、取消、查重和状态推进。
- **视频处理器**：只处理视频模式特有阶段。
- **漫画处理器**：只处理漫画模式特有阶段。
- **公共 service**：提供文本模型、图片模型、视频模型、配音、存储、队列、媒体和发布能力。
- **状态投影器**：把任务、阶段、产物和回执组合为前端所需的唯一状态视图。

### 4.2 依赖边界

```text
api/modules/batch-factory/
  command/       执行命令
  workflow/      单书流程与阶段图
  video/         视频阶段处理器
  comic/         漫画阶段处理器
  status/        权威状态查询
  repository/    模块数据访问

api/service/
  textmodel/ imagemodel/ videomodel/ tts/
  storage/ queue/ media/ publisher/

前台/src/modules/batch-factory/
  commands/ status/ video/ comic/ components/
```

模块只能依赖自身、`service`、`prompt` 和平台底座。视频与漫画不能读取对方内部状态。系统提示词统一保存在后端 `prompt` 模块。

## 5. 权威数据模型

新增数据结构使用 MySQL 保存，Redis 只承担队列、延迟任务和短期锁。新表只保存任务事实和已有业务产物的编号，不复制视频、图片、音频或合集正文。

### 5.1 执行任务

记录一次用户意图：

- 所属用户和批次。
- 视频或漫画模式。
- 目标状态，例如 `published_confirmed`。
- 创建来源：立即执行、定时执行或恢复执行。
- 当前总状态和统计。
- 前端请求编号。
- 创建、启动、完成和取消时间。

### 5.2 配置快照

记录任务启动时使用的：

- 模型与模型配置版本。
- 预设编号、版本和生产模式。
- 系统提示词版本和用户约束版本。
- 发布组织、分类和映射配置。
- 内容范围、并发、音频、合成和画幅参数。
- 快照摘要值，用于判断能否复用阶段结果。

快照创建后不可修改。

### 5.3 单书流程

每个执行任务中的每本书保存：

- 当前阶段和当前状态。
- 下一次可执行时间。
- 是否请求重试。
- 是否等待外部结果。
- 是否需要人工处理。
- 最近一次错误分类和中文说明。
- 已关联的正文、提示词、媒体、合集和发布回执编号。

### 5.4 阶段运行

每本书的每个逻辑阶段保存一条阶段运行记录：

- 阶段编号和状态。
- 输入指纹和输出产物编号。
- 当前有效尝试编号。
- 下一次执行时间和租约信息。
- 是否允许跳过、重试或人工恢复。

输入指纹由该阶段真正依赖的上游产物编号、配置字段和提示词版本组成。只有输入指纹相同、输出产物仍可读取时才能复用成功结果。正文等与模型配置无关的产物可以跨快照复用；模型生成和合成结果必须满足各自阶段的输入指纹。

### 5.5 阶段尝试

每次调用模型、合成、上传或回读都保存：

- 唯一尝试编号。
- 书籍、阶段和配置快照。
- 请求摘要，不保存明文密钥。
- 供应商任务编号。
- 状态、重试次数和时间。
- 产物编号。
- 错误类别、清洗后的错误信息和受控原始响应。

一次逻辑阶段可以有多次物理尝试，但同一时刻只能有一个有效尝试。重试创建新的尝试记录，不覆盖旧记录。

### 5.6 发布回执

保存：

- 固定提交编号。
- 外部平台和组织。
- 请求时间和接收状态。
- 外部记录编号。
- 最后回读时间和回读结果。
- 是否确认存在匹配记录。

### 5.7 待发送事件

保存需要投递到 Redis 的任务事件。任务状态和待发送事件在同一个 MySQL 事务内写入；投递成功后记录发送时间。Redis 暂时不可用时，后台投递器继续重试，不丢失业务任务。

## 6. 状态模型

### 6.1 单书状态

```text
pending → running → waiting_external → completed
                  ├→ retry_wait
                  └→ needs_attention
pending/running → cancelled
```

中文显示分别为：待执行、执行中、等待外部结果、已完成、等待重试、需要人工处理和已取消。

执行任务本身使用 `planned`、`running`、`needs_attention`、`completed` 和 `cancelled`。只要仍有书可继续，单书的 `needs_attention` 不会把整个执行任务改成停止状态；全部可执行书处理完后，仍存在人工处理书籍时，任务才进入 `needs_attention`。

### 6.2 阶段状态

```text
pending → queued → running → succeeded
                         ├→ reconciling
                         ├→ retry_wait
                         └→ terminal_failed
pending/queued → skipped/cancelled
```

### 6.3 完成判定

一本书只有同时满足以下条件才允许进入 `completed`：

1. 正文和分类已经确定。
2. 目标模式所需资产、提示词和媒体全部成功。
3. 最终成片或漫画合集存在，并且产物记录可读取。
4. 上传或发布请求已被外部平台接收。
5. 外部平台回读找到匹配记录。
6. 回读记录与当前书、当前执行任务和当前提交编号一致。

其他状态必须使用准确名称：

- 合成成功：成片已就绪。
- 上传接口接收：已提交待确认。
- 上传结果未知：上传结果待核对。
- 外部回读确认：已完成。

## 7. 幂等和重复执行

执行请求的查重键为：

```text
用户 + 批次 + 书籍 + 目标状态 + 配置快照版本
```

重复请求遵循：

- 已成功阶段直接复用。
- 正在运行的阶段返回原任务。
- 可重试失败阶段加入原任务队列。
- 新选择的书籍补入当前执行任务。
- 已提交待确认的任务只回读，不重新上传。
- 配置变化创建新快照，但与配置无关的正文和可兼容产物仍可复用。
- 强制重做必须由用户明确选择并二次确认。

“可兼容产物”必须通过阶段输入指纹判断，不能只比较模型名称或根据文件存在与否推断。强制重做会生成新的阶段运行版本，不删除旧产物和旧尝试记录。

每个阶段执行前先在 MySQL 创建唯一尝试记录。Redis 锁只能避免多个工作进程同时领取，最终能否执行必须再次由 MySQL 状态决定。

## 8. 错误分类与处理

| 错误类别 | 处理方式 |
|---|---|
| 网络超时、限流、供应商繁忙 | 延迟重试，最多 3 次 |
| 阶段正在执行、版本冲突 | 等待后重新读取，不计模型失败 |
| 模型输出格式错误 | 使用修复指令重试，最多 2 次 |
| 内容审核不通过 | 使用安全改写提示词重试，最多 2 次 |
| 模型、密钥、组织或发布配置缺失 | 该书进入需要人工处理 |
| 无权限、余额不足 | 立即停止，不自动重试 |
| 已扣费但结果未取回 | 只查询原供应商任务，不重新生成 |
| 上传结果未知 | 只回读核对，不直接重传 |
| 前置产物缺失 | 返回缺失的前置阶段补齐 |
| 数据关系损坏 | 转人工处理，不猜测执行 |

一本书失败不阻塞其他书。自动重试书籍排到队尾；批次首轮处理结束后再集中补跑。最终仍失败的书进入 `needs_attention`，成功书保持完成状态。

内容审核处理必须保存原始提示词版本、安全分类、安全改写版本、采用的安全规则和最终结果。普通页面不显示敏感原文。

## 9. 执行接口

主要入口：

```http
POST /api/batch-factory/v12/batches/{batchId}/executions/ensure
```

请求：

```json
{
  "bookIds": ["book-1", "book-2"],
  "mode": "video",
  "target": "published_confirmed",
  "clientRequestId": "request-xxx"
}
```

响应：

```json
{
  "executionId": "exec-xxx",
  "created": false,
  "attached": true,
  "reusedBooks": 8,
  "queuedBooks": 12,
  "reconcilingBooks": 2,
  "blockedBooks": 1
}
```

辅助接口：

```text
GET  /executions/{id}
GET  /executions/{id}/books/{bookId}
POST /executions/{id}/resume
POST /executions/{id}/cancel
POST /executions/{id}/reconcile
```

前端不能再通过阶段接口自行编排完整批量流程。阶段接口仅保留给受控的单步人工操作和兼容旧任务使用。

## 10. 数据流和队列可靠性

```text
接收请求
→ MySQL 事务查重
→ 创建或复用任务
→ 冻结配置
→ 计算缺失阶段
→ 写任务与待发送事件
→ Redis 通知工作进程
→ 工作进程领取阶段
→ MySQL 再次确认执行权
→ 调用 service
→ 保存结果和产物
→ 推进下一阶段
→ 上传后持续回读
→ 外部确认后完成
```

写任务和发送 Redis 消息之间使用 MySQL 待发送事件。后台投递器负责重试未发送事件，从而避免数据库写成功但队列消息丢失。

工作进程领取任务后保存租约和心跳。租约过期时，新的工作进程先检查已有供应商任务编号和产物，再决定继续查询或重新执行。

## 11. 前端设计

### 11.1 批量操作

主按钮继续使用“立即执行已选（N）”。点击后展示预检：

- 已经完成并复用的书。
- 需要继续生产的书。
- 只需核对上传结果的书。
- 配置阻塞的书。

确认后，已有相同任务就补入当前任务，不向用户显示笼统冲突。

### 11.2 顶部统计

任务状态互斥，并且总和必须等于批次书籍数。`retry_wait` 计入执行中，`waiting_external` 计入等待外部确认，`needs_attention` 计入需要处理，取消单独统计：

```text
已完成 + 执行中 + 等待外部确认 + 需要处理 + 尚未执行 + 已取消 = 总书籍数
```

分镜、可播放视频和成片属于产物统计，必须与任务状态分开展示。

### 11.3 单书显示

每本书只显示一个当前主状态，展开后再显示完整时间线和历史失败。后续成功必须压过历史失败。

### 11.4 重试和取消

- 继续失败书籍只补跑受影响阶段。
- 配置错误提供直接配置入口。
- 取消只阻止尚未发出的阶段。
- 已发送给模型的任务继续回收结果。
- 已提交内容继续回读，不重新上传。

### 11.5 组件拆分

```text
BatchFactoryPage
├─ BatchToolbar
├─ BatchStatusSummary
├─ BookProductionRow
├─ ExecutionPreflightModal
├─ ExecutionTimeline
├─ VideoProductionPanel
├─ ComicProductionPanel
├─ PublicationReceiptPanel
└─ TaskLogDrawer
```

状态计算放在后端统一状态接口，前端组件只负责渲染和提交命令。

## 12. 旧任务兼容与迁移

迁移期间禁止新旧系统同时修改同一本书：

- 活动旧任务继续由旧执行器完成。
- 新入口发现活动旧任务时，创建等待记录并关联旧任务，不返回冲突。
- 旧任务结束后，新内核读取实际产物并只补缺失阶段。
- 旧任务状态只读，不进行双写。
- 新任务只写新状态表。
- 统一查询同时读取新状态和旧状态投影。
- 前端完成切换后再删除旧状态拼接。

迁移顺序：

1. 新状态合同和数据库表，只读映射旧状态。
2. 统一执行入口、查重、配置快照和恢复机制。
3. 视频生成、音频和合成阶段。
4. 上传和外部回读阶段。
5. 漫画生成、合集和发布阶段。
6. 前端拆分和旧执行入口清理。

所有数据库修改在迁移期只新增表和字段，不删除旧数据。新内核由功能开关控制，任何阶段可以独立回退。

## 13. 测试设计

### 13.1 状态与配置

- 状态只能按允许方向流转。
- 完成必须有外部确认回执。
- 历史失败不能覆盖后续成功。
- 视频任务不能使用漫画预设，反之亦然。
- 配置快照不可修改。

### 13.2 幂等与并发

- 连续点击十次只创建一个有效阶段任务。
- 两个浏览器同时点击不重复生成。
- 定时和立即执行同时触发只执行一次。
- Redis 锁失效后 MySQL 仍阻止重复调用。
- 服务重启后继续查询原供应商任务。

### 13.3 单书隔离

- 一本书配置错误不阻塞其他书。
- 内容审核只重试对应书和阶段。
- 批次可以部分完成，成功书不重新标红。
- 修复配置后只恢复失败书。

### 13.4 上传与回读

- 已接收但未回读时保持待确认。
- 上传超时先查询，不直接重传。
- 外部已存在相同提交编号时不重复上传。
- 取消后已提交内容仍继续回读。

### 13.5 兼容和故障演练

- 旧任务可显示并安全接续。
- 模拟模型错误格式、限流、审核拒绝、Redis 重启、MySQL 短暂断开、TOS 超时、服务重启和磁盘不足。
- 每种演练必须证明不重复扣费、不重复上传、不丢产物、不阻塞其他书，并且页面状态与数据库一致。

## 14. 监控和告警

持续统计：

- 各阶段排队、执行、成功和失败数量。
- 长时间未更新的任务。
- 自动重试次数和错误类别。
- 已扣费待取回数量。
- 上传结果待核对数量。
- 重复请求安全复用次数。
- Redis 队列与 MySQL 待执行记录差异。
- TOS 上传耗时和失败率。
- 本地和线上磁盘使用率。
- 当前运行版本、前端入口和数据库迁移版本。

告警优先级：

- 立即处理：重复上传风险、重复扣费风险、数据库状态不一致。
- 高优先级：任务超时、外部回读持续失败。
- 普通告警：供应商限流、单书审核失败。
- 信息记录：重复请求被复用、旧任务完成后自动接续。

日志不得输出 API Key、Cookie、Authorization 或密码。

## 15. 验收标准

使用包含正常书、审核敏感书、配置缺失书和已有成片书的小批次验证：

1. 重复点击不重复生产。
2. 已有成片被复用。
3. 配置缺失书不阻塞其他书。
4. 内容审核按规则安全重试。
5. 服务重启后任务恢复。
6. 上传结果不明时只回读核对。
7. 外部平台确认后才显示完成。
8. 页面状态总数始终等于书籍总数。
9. 日志不泄露凭证。
10. 本地、GitHub 远端和线上对应同一份已验证代码。

## 16. 发布和回退

每个迁移阶段固定执行：

1. 本地代码和数据库迁移。
2. 本地测试、前端构建和 Go embed。
3. 本地 `4001` 实际运行验证。
4. 推送到 `cui1112233/yzcm` 远端。
5. 构建单个 Go 程序并部署线上。
6. 校验线上版本、健康状态和数据库迁移。
7. 使用小批次真实任务验收。
8. 观察稳定后扩大批量范围。

每次交付保留三组证据：

- 本地：`4001` 健康检查、运行版本、页面和任务结果。
- 远端：GitHub `main` 提交号和测试记录。
- 线上：运行版本、健康检查、真实任务结果和外部回读结果。

回退时只关闭新任务入口，不丢弃已经进入模型或上传阶段的结果。数据迁移只新增结构，因此可以恢复旧入口读取旧状态。任何阶段只回退本阶段，不覆盖已确认成功的业务数据。
