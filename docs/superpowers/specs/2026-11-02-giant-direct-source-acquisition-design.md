# 巨量素材：直取优先的原文获取任务设计

- 日期：2026-11-02
- 状态：待用户审阅
- 覆盖：2026-10-02 设计中“直取失败自动 OCR”的行为；该行为不再适用于 `direct_first`。

## 目标

“优先直接获取原文”必须是一个完整、可追溯的后端策略，而不是前端页面上的一次请求。

```text
direct_first
  -> 书城直取成功：保存完整原文，处理、分类，再允许生产
  -> 书城直取失败：source_blocked，保存失败证据，停止
  -> 用户点“使用 OCR”且执行器在线：才创建 OCR 任务
```

书城直取失败后，任何自动化、刷新页面、定时调度或恢复任务都不得创建 OCR，也不得再次请求书城。

## 问题与根因

1. 读取策略和状态保存在 `sourceMetadata`，但批量创建、书卡恢复、OCR 队列和自动生产分别解释它。
2. 自动生产的 `ensureAutomationSource` 会对空正文再次调用书城抓取，能够绕过前端的失败停止逻辑。
3. `contentPending` 同时表示读取中、OCR 等待和直取失败，造成列表与日志出现互相矛盾的提示。
4. 巨量解析只保存书城名称、候选平台编号和 Book ID；121 返回“参数不完整”时没有保存用于诊断的参数来源和校验结果。

## 方案选择

### 第一阶段：立即收口（本次实施）

- 后端将 `direct_first + direct_failed` 视为终止的原文状态。
- 自动生产启动前和每本书推进前都检查该状态；命中后写 `blocked/source`，不再自动抓取、OCR 或生产。
- 新建批量在存在直取失败书时不自动启动生产；已存在的自动化任务转为“等待人工处理”。
- 将失败书从“正在后台读取”计数中移除，统一显示“书城原文获取失败”。
- 对巨量直取执行本地预检：数字书城编号、Book ID、解析来源必须完整；不完整时不请求 121。
- 保存非敏感诊断：原始策略、书城编号、编号来源、Book ID、尝试次数、上游状态码、可读错误、发生时间。

### 第二阶段：统一原文获取任务

新增 MySQL 持久化的 `source_acquisition_jobs`。任务由后端领取和推进，前端只创建策略、查看状态、发起人工动作。

字段至少包括：批量、书、方式（direct/ocr）、策略、状态、尝试次数、可否重试、请求参数摘要、上游错误、OCR 任务编号、创建/开始/结束时间。

状态机：

```text
pending_direct -> direct_running -> source_ready
                               -> direct_failed -> source_blocked
source_blocked --用户选择 OCR--> ocr_dispatching -> ocr_queued -> ocr_running -> source_ready
```

`direct_failed` 和 `source_blocked` 是不同语义：前者记录本次动作结果，后者明确表示后续自动链路不得接管。

### 第三阶段：与小说获取共用处理核心

无论来源是 121 书城还是 OCR，正文成功保存后都调用同一个 Go 处理服务：

```text
完整原文保存 -> 规则处理 -> 敏感词处理 -> 男女频/风格分类 -> 允许生产
```

保留来源差异和完整原文，不让 OCR 文本覆盖书城原文，也不让处理正文覆盖原文。

## 后端边界

### 原文状态门禁

新增一个只读判定函数，供自动生产、定时调度、恢复任务和手动生产共同使用：

```text
可生产：source_ready + 分类完成/人工确认
待人工：source_blocked
可等待：direct_running / ocr_queued / ocr_running
```

不得在 `ensureAutomationSource` 内为 `source_blocked` 回退抓取。对其他历史空正文保留兼容抓取，但必须记录为 `legacy_auto_recovery`，不能误用于 `direct_first`。

### 参数预检与诊断

将巨量解析结果规范为：`platformId`、`platformIdSource`、`platformName`、`platformBookId`、`giantMaterialId`。

若 `platformId` 不是支持的数字平台或 `platformBookId` 为空，返回稳定错误码 `GIANT_DIRECT_SOURCE_UNAVAILABLE`，并提示“巨量解析未提供可用于书城直取的书城编号或 Book ID”。不再把无效参数交给 121 后才得到笼统的 400。

调用 121 后保存响应状态和业务码，但绝不保存令牌、Cookie、完整视频地址或授权头。

## 前端行为

列表和日志只从后端状态映射显示：

| 状态 | 显示 | 操作 |
|---|---|---|
| `direct_running` | 正在书城获取原文 | 无 |
| `source_blocked` | 书城原文获取失败 | 重试直取、使用 OCR |
| `ocr_queued` | OCR 等待执行器 | 取消、查看执行器 |
| `ocr_running` | OCR 识别中 | 查看进度 |
| `source_ready` | 原文已获取 | 查看原文 |

失败书不进入“正在后台读取”统计，也不展示“等待正文读取”。OCR 按钮在未发现在线执行器时禁用，并说明不会创建队列任务。

## 验收

1. `direct_first` 的 121 失败不会创建 OCR、不会重试 121、不会启动生产。
2. 页面刷新、关闭浏览器、定时调度和服务恢复后仍满足第 1 条。
3. 用户手动选择 OCR 且执行器在线后，才产生一条 OCR 任务。
4. 执行器离线时点击 OCR 不产生任务。
5. 失败书不计入“后台读取中”，列表、详情和日志表达一致。
6. 缺少平台编号或 Book ID 时不调用上游；121 返回错误时可看到参数来源和稳定错误码。
7. 正文成功后保存完整原文、处理正文与分类结果，并仅推进该本书的后续生产。

## 测试

- Go：原文状态门禁、自动生产不绕过 `source_blocked`、定时恢复不绕过、参数预检、121 业务错误记录。
- 前端：失败状态映射、离线 OCR 按钮、失败统计、手动 OCR 操作。
- 端到端：直接失败 -> 刷新 -> 定时调度 -> 无 OCR/无生产；人工 OCR -> 正文保存 -> 分类 -> 单书生产。

## 不做

- 不自动猜测或枚举书城平台编号。
- 不将 OCR 作为 `direct_first` 的隐式回退。
- 不在前端保存上游授权信息。
- 不为验证本改动触发付费模型、视频生产或发布。
