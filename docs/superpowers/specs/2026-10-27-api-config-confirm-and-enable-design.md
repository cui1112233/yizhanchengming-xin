# API 配置确认与自动启用设计

## 目标

统一“平台预设模型”内所有配置卡的操作方式，减少“先保存、再开开关”的重复步骤，并明确区分未配置、保存中、已启用和可修改状态。

本次只调整 `API 配置 -> 平台预设模型`，覆盖 YD2.0 Mini、MiniMax H3、Seedance 2.0 官方、梵客视频 API，以及以后使用同一卡片结构新增的预设模型。自定义模型弹窗不在本次范围内。

## 统一交互

### 未配置

- API Key 及该卡片的其他配置字段均可编辑。
- 开关显示关闭，但允许点击。
- 操作按钮显示“确定配置”。
- 用户没有填写 API Key 就尝试打开开关时，不发保存请求，Toast 提示“请输入 API Key”。
- 单纯点击或输入 API Key 时不主动弹 Toast。

### 确定配置

- 点击“确定配置”后提交当前卡片的完整配置。
- 按钮进入 loading 状态并显示“保存中”，防止重复提交。
- 保存期间输入项、开关和按钮均不可重复操作。
- 后端保存成功后自动把该模型设为启用，不要求用户再次点击开关。
- 成功 Toast 统一显示“配置已保存”。
- 保存失败时保持关闭状态，保留用户刚输入的内容，并显示后端返回的失败原因。

### 已启用

- 开关显示开启。
- API Key、Relay 地址、工作流 ID、模型选择等整组配置全部锁定。
- 按钮显示“配置已保存”并不可点击。
- 用户点击锁定的配置区域时，Toast 提示“请先关闭开关，再修改配置”。

### 修改配置

- 用户先关闭开关，前端立即向后端保存停用状态。
- 停用成功后整组字段恢复可编辑，按钮恢复为“确定配置”。
- 已保存的 API Key 不回显；输入框提示“留空表示不修改已保存的 Key”。
- 用户修改任意配置并再次点击“确定配置”后，保存成功并自动重新启用。
- 停用失败时恢复开关开启状态，配置继续锁定，并显示失败原因。

## 状态与数据流

每张预设卡按模型 ID 单独维护保存状态，避免保存一个模型时让所有卡片一起转圈。

1. 页面加载服务端模型数据。
2. 用户编辑当前卡片的本地草稿。
3. “确定配置”提交完整草稿，并固定提交 `enabled: true`。
4. 请求成功后清空前端明文 Key，重新读取模型列表与额度状态。
5. 服务端返回 `enabled: true` 且配置完整时，卡片进入已启用锁定状态。
6. 关闭开关只提交 `enabled: false`，成功后卡片进入可编辑状态。

服务端仍是配置状态的唯一依据，前端不使用临时假开启状态掩盖保存失败。

## 校验规则

- 首次配置必须填写 API Key。
- MiniMax H3 同时保存工作流 ID；未填写时使用现有默认工作流 ID。
- 梵客视频 API 同时保存当前选择的模型。
- 带 Relay 地址的预设同时保存当前 Relay 地址。
- 已有服务端凭据的模型允许停用后只修改其他字段；Key 留空表示沿用旧 Key。
- 配置不完整时点击开关只提示，不提交请求。

## 界面文案

- 默认按钮：`确定配置`
- 保存中按钮：`保存中`
- 已完成按钮：`配置已保存`
- 缺少 Key：`请输入 API Key`
- 已锁定提示：`请先关闭开关，再修改配置`
- 成功提示：`配置已保存`

## 验证范围

- 四张平台预设卡都使用相同按钮文案和状态切换。
- 未配置时点击开关会出现缺少 Key 的 Toast。
- 确定配置期间只有当前卡片显示 loading。
- 保存成功后自动启用并锁定整张卡片。
- 关闭开关后所有配置项恢复可编辑。
- 修改配置并再次确认后自动重新启用。
- 保存或停用失败不会产生错误的视觉状态。
- 前端测试、构建、Go embed 构建和本机浏览器交互全部通过。
