# 小说获取与 REA 全链路审计、刷新恢复设计

日期：2026-11-02
范围：小说获取任务的阶段日志、页面刷新后的任务状态恢复、定时任务派发恢复和重复入队保护。
参考：REA 批量原文改文系统的完整任务链路，以及现有小说获取与批量工厂的运行实现。

## 目标

让用户在小说获取页面能回答三个问题：每本书当前在哪一步、上一步发生了什么、刷新页面或服务短暂中断后任务能否继续或给出明确状态。定时任务派发和手动/自动提交同时发生时，同一本书只能有一个有效队列任务。

本轮只补齐观察、恢复和防重复的基础能力，不改变原文抓取、敏感词处理、男女频/风格判断、改写或提交的业务规则。

## 对标结论

REA 的可借鉴点是把处理过程拆成可观察的阶段，并让每本书的状态独立推进、失败可定位、卡住任务可恢复。小说获取已有队列、持久化原文和正文版本、超时恢复及若干等待状态，但当前运行进度部分依赖内存；阶段日志不够统一，页面刷新后不一定能还原细节；定时任务 `dispatching` 中断恢复和并发重复提交保护也需要明确规则。

因此本轮沿用现有 Go/MySQL/Redis 责任边界，不复刻 REA 的 Python/本地 JSON 存储，也不另建一套任务系统。

## 设计

### 1. 统一阶段审计

小说获取每个任务以书籍为单位记录阶段事件。至少覆盖：任务创建、抓取开始/成功/失败、原文落库、规则处理开始/完成/失败、敏感词处理等待/开始/完成/失败、分类开始/完成/失败、改写开始/完成/失败、提交开始/完成/失败、重试安排、任务恢复和任务终止。

每条事件包含任务/书籍标识、阶段、事件类型、发生时间、可安全展示的结果摘要或失败原因，以及必要的尝试次数。日志不得包含 API 密钥、Cookie、完整认证头或整本正文。阶段日志追加保存，不得因刷新或后续阶段覆盖旧记录；现有日志长度限制需改为有界保留并明确排序/分页，避免无限增长。

页面按时间顺序展示近期阶段与当前阶段，等待状态必须说明等待原因；刷新后从服务端读取任务和事件，不把“刷新时内存为空”误报为任务失败或完成。

### 2. 刷新与进程恢复

服务端持久化状态是任务当前阶段的依据，前端运行态仅用于即时反馈。刷新时重新读取任务、阶段、重试时间和阶段日志。进程启动或恢复扫描时，对超时且仍处于执行中的任务进行租约/更新时间校验：可安全继续的任务回到对应队列等待；无法确定是否可重放的外部提交不自动重复执行，而是标记为待核验并保留原因。

恢复操作本身写入阶段日志。已完成的阶段不因恢复重新执行；恢复不得覆盖完整原文、已保存处理正文或已生成版本。

### 3. 定时任务派发恢复

定时触发进入派发流程时，记录派发标识、预期任务、开始时间和结果。`dispatching` 超过明确超时后，由恢复扫描检查关联任务是否已创建或已进入队列：已创建则将派发记录补记为完成；未创建且没有有效执行者时，允许再次派发；状态不完整或结果不确定时保留为可观测错误并避免盲目重复执行。

恢复扫描必须有并发保护，同一派发记录同一时间只允许一个恢复者处理。超时阈值和扫描频率沿用项目已有配置/调度模式；若当前没有合适配置，则使用有命名的默认值并通过测试锁定，不新增用户界面配置项。

### 4. 重复入队保护

在服务端创建/入队的最终写入边界执行幂等校验，不能只依赖前端先查询再提交。对于同一账号、平台和来源书籍标识，存在仍有效的抓取/处理队列任务时，重复请求返回已有任务及明确结果，不再新增第二个有效执行。

已完成任务再次抓取、创建新正文版本或加入新的批次属于不同用户意图，必须通过现有明确操作/版本语义区分，不能被永久去重规则误拦截。并发请求的保护使用现有数据库唯一约束、事务锁或 Redis 锁等与现有架构匹配的机制，并保证锁失效后仍有数据库层兜底；具体选型以当前仓库已有持久化模型为准。

## 状态与失败规则

- `queued` 表示任务已持久化并等待执行；`running` 必须带当前阶段和最近更新时间。
- 等待抓取重试、等待敏感词处理、等待分类/改写或等待配置等状态保留其具体阶段和原因，不压成单一“处理中”。
- 阶段成功后写入完成事件和持久化结果，再推进下一阶段；失败写入安全可见的错误摘要和下次重试信息（若已有）。
- 日志写入失败不得把正文结果伪装为失败或重复执行业务；要返回/记录可诊断错误，并由恢复检查补齐可推导事件。
- 重复请求返回既有任务标识，前端显示“任务已存在/正在处理中”，不得显示为新任务已创建。
- 外部提交的结果不确定时进入待核验，不能因服务重启自动再次提交。

## 验证

先写失败测试，再实现。覆盖：

1. 各业务阶段会追加可查询的审计事件，敏感认证信息不会进入日志。
2. 前端刷新后从服务端还原当前阶段、等待原因和事件；服务端重启恢复不重跑已完成阶段。
3. 超时 `dispatching` 在任务已创建、未创建和状态不确定三种情况下分别正确补齐、重派或阻止盲目重派。
4. 两个并发的同书请求只产生一个有效队列任务；已完成任务经明确重新抓取操作仍可建立新运行。
5. 待核验的提交不会在恢复扫描中被再次提交。

运行小说获取相关 Go 单测与 API 测试、对应前端状态/刷新测试；检查格式与数据库迁移兼容。不得为验收触发真实外部抓取、付费 AI 调用、视频管理系统提交或部署。

## 本轮不做

- 不实现各阶段独立重试按钮/接口和批量阶段重试。
- 不调整抓取、AI、敏感词等各自并发数或限流策略。
- 不改变分类规则、敏感词规则、改写提示词、正文截断和提交业务逻辑。
- 不改版批量工厂或将其任务入口迁移到小说获取队列。
- 不重写队列架构，不照搬 REA 的 Python/JSON 文件实现。
- 不部署公网、不重启运行服务，不执行真实外部任务。
