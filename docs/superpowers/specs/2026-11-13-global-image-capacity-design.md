# 全站图片并发控制方案（用户已确认实施）

## 已确认目标

所有用户、批次和单本书共享上游额度。用户多时排队、空闲时充分利用，取消单本固定 4 路作为唯一控制手段。实测依据见 docs/acceptance/2026-11-13-low-price-image-capacity-results.md。

## 推荐方式

采用“管理员上限＋运行中自动调整”：0.019 通道在本轮已测试的 1024x1536、无参考图请求方式下硬上限 20，初始运行值 12。自动调整只使用真实生产的成功率、耗时和限流反馈，不后台额外生成收费测试图；限流或持续传输失败时降速，经过冷却并连续稳定后每次恢复 1 路，始终不超过管理员上限。

另外两种方式是固定上限（更简单，但不能应对通道波动）或运行中无限探测上限（会产生额外费用和不可控负载，不采用）。目前不能将一次 20 路成功宣称为绝对极限。

## 分组和控制范围

- 上游账号总池与账号下各模型池同时生效；同一凭据的不同别名不能拆开额度。不同密钥所属同一账号时支持管理员明确归组，普通用户不可通过复制配置扩大总量。
- 0.019 与 0.034 已确认使用相同凭据，归同一账号总池。0.034、0.0064 的模型并发未验证，先保留现有保护值；其他尺寸和带参考图请求也不直接套用已测额度。
- 生产表、资产图、漫画页、单页/失败重试、旧批量出图、Agent、参考资产及渠道执行入口统一领取名额；转发给本地豆包执行器的任务保留执行器自身能力约束。

## 保存与排队

管理员策略和分组保存在 MySQL；Redis 统一保存等待队列、账号/模型在用名额、任务租约和短时调整状态。所有 Go 服务实例共用 Redis。领取、续期、释放用原子操作，任务唯一编号防止重复释放或重复领取，进程重启不能把旧在途当空闲。

排队按用户及书籍轮转，避免一个用户先塞入大量页独占后续名额。只有一本书等待时，它可以用满可用额度，多本书等待时动态分配。停止未发出请求只撤销等待；已提交任务等待明确结果，不能一边归还名额一边偷偷继续生成。Redis 不可用时暂停新提交并显示原因，不绕过限制直连。

## 完成、失败与恢复

收到响应头不算生成完成；同步接口直到完整有效图片结果取回才归还生成名额，异步接口直到供应商任务进入终态。超时但上游可能继续生成时保留待核对占用，直到结果核对或该通道明确的安全期限，避免取消后立即再提交导致实际超额。

HTTP 429、供应商明确并发限制按 Retry-After 冷却并降速。余额不足、密钥错误、内容拒绝、图片下载 403 单独分类；不因这些错误学习出错误的容量。降低上限不杀已提交请求，等待在途自然回落后再放行；不自动重发已可能计费的生成请求。

## 界面

普通用户的统一配置展示“自动分配”，同时可见当前通道全站运行数、上限、排队情况；不再把每用户或每本书的 4 路选项当成模型总限额。管理员可查看账号/模型分组、设置总上限及自动调整范围，未知通道标注“并发未实测”。排队不显示“生成失败”，用户可区分等待、生成中、冷却和配置异常。

## 验收

在隔离 Redis 测试中模拟多个用户、多个书籍、两个 Go 实例，证明账号和模型总量均不超限；验证排队公平、取消、重复释放、租约恢复、降上限、Redis 故障、限流冷却、凭据别名去重。通过模拟上游验证所有出图入口都经过统一闸门，响应头提前到达时不提前归还。
