# YZCM 托管模型、团队独立余额与管理员自动开户

日期：2026-11-25  
状态：设计待书面复核，尚未实施本方案。  
维护主线：一战晟铭 `v88`；按用户要求直接维护当前主线，不另建分支。

视觉评审稿：`docs/design/yzcm-center-20261125/index.html`，含12个页面场景及关键弹窗；演示数据与实际接口独立，详细目录和查看方式见同目录 `README.md`。其中 API 配置的旧稿以第 5.1 节最新确认的操作流程为准；旧稿中的团队默认 Key 独立面板、模型右侧配置区和生产模式组合卡片不作为本次 API 配置的实施依据。

## 1. 目标与边界

管理员在一战晟铭选择 YZCM 模型、填写 Key，无须填写请求地址；成员直接使用团队配置。每个独立团队有自己的 YZCM 消费账号、充值余额和账单。一战晟铭继续把共享 Key 的调用归属到实际操作成员。

管理员新增界面提供默认勾选的“同时开通 YZCM API 账号”。已有管理员提供批量检查、开通和失败重试。两站使用同名账号和相同密码。

本次不改模型价格，保留 `gpt-image-2.6-flare` 人工价格 ¥0.049/次；不补造历史共享 Key 的成员归属；不把尚未完成的视频异步最终扣费说成已实现；不自动生成模型 Key，不增加第二套扣款。

## 2. 角色与账号关系

| 对象 | 职责与权限 |
| --- | --- |
| 平台维护者 | 维护 YZCM 通道、价格、全量模型目录及平台允许使用的模型 |
| 团队管理员 | 管理本团队消费账号、充值、Key、模型预设和成员权限 |
| 团队成员 | 使用团队授权模型，查看自己的调用与制作；按权限查看团队统计 |
| YZCM 自动开户账号 | 普通消费账号，可充值、查看自身账单和管理自身 Key；不授予 YZCM 平台管理员权限 |

以稳定的本地团队/配置归属标识绑定 YZCM 用户 ID，用户名只用于登录和展示。一个独立团队只绑定一个消费钱包；同一团队增加管理成员不能额外生成另一个收费钱包。现有每位独立团队负责人分别开通账号；执行批量开通前先按实际团队关系去重。

绑定后改用户名不重新开户；删除或停用本地管理员不自动删除 YZCM 余额及账单。停用团队时禁止其成员发起新请求，并停用团队专用 Key；已经在途请求照常核账。

## 3. 自动开户流程

1. 创建一战晟铭管理员时默认勾选“同时开通 YZCM API 账号”；取消后只创建本地账号。
2. 本地账号先落库，记录开户任务；通过受保护的两站后端接口创建普通消费账号并建立绑定。
3. 状态统一为“未开通 / 待开通 / 已开通 / 开通失败”，失败显示简短原因并可重试。
4. 每个任务携带稳定团队标识和幂等标识。请求超时后先查询已有绑定再重试，禁止重复建号。远端创建成功但本地回写失败时必须能重新找回远端 ID。
5. 开户失败不回滚已创建的一战晟铭账号，也不能把状态伪装成成功；需要模型调用时明确提示先完成开通和 Key 配置。
6. 现有管理员批量开通先展示检查结果：可开通、已绑定、账号冲突、名称不兼容。冲突项不覆盖旧账号、密码或余额，保留人工核对入口。

同名 YZCM 账号不能凭名字自动认领。只有带相同系统来源和稳定团队标识的绑定可以自动恢复；已有普通账号需核实所属后人工关联。

## 4. 相同账号密码：统一验证

当前一战晟铭保存 scrypt 密码摘要，YZCM 保存 bcrypt，不能直接复制摘要或找回旧密码。采用“绑定账号由一战晟铭验证密码”的方案：

- YZCM 对已绑定账号走受保护的服务端验证接口；一战晟铭验证密码、账号启用状态和绑定关系。返回必要身份结果，不返回密码摘要。
- 用户新密码只在当前登录/改密请求中短暂处理，不保存明文，不写入日志、任务或缓存。服务间使用 HTTPS 或经过验证的加密隧道，禁止通过公网 HTTP 传递密码和 Key。
- 已绑定账号的改密、找回密码统一进入一战晟铭的验证流程，YZCM 原有改密/找回/管理员编辑入口不能另设一份密码绕开它。
- 一战晟铭改密后，两站下次登录即使用新密码；按两站已有会话撤销规则撤销旧会话。禁用账号同样拒绝新登录。
- 验证服务不可用时明确显示暂不可登录，不回退到空密码或旧密码，也不绕过检查。登录频率限制和错误信息应避免泄露账号是否存在。
- YZCM 原生账号、平台维护者/root 保持原生验证，不强制改为桥接登录，保留维护入口。

绑定账号支持一战晟铭现有 8–128 位密码范围，不受 YZCM 原生注册 8–20 位校验限制；该差异只针对明确标记的绑定账号。用户名仍需兼容两站：开通前检测 YZCM 当前 20 字符限制，超限列为阻塞项，不偷偷截断或改名。

服务接口必须限定调用方、接口权限、请求有效期和防重放；浏览器不持有开通账号的管理凭据。账号创建、绑定、停用和手工关联记审计记录。生产加密连接未验证前不得开启跨公网密码验证。

## 5. 模型目录与自定义预设

模型目录采用三层选择：

1. YZCM 全量目录由后台主动同步并保存，记录更新时间和同步结果。
2. 平台维护者筛选已适配、允许使用的模型；未适配的协议不直接出现在生产下拉框。
3. 团队管理员在现有“自定义预设”弹窗中搜索并勾选模型，确认后回到 API 配置主页面，在对应模型下面填写 Key。

生产页面按文字、图片、视频、配音等能力筛选，只显示团队默认/常用模型，支持搜索与“更多模型”。不在每次打开下拉框时实时访问上游；目录同步失败继续显示上次有效目录和更新时间，不能清空配置。

自定义预设仅选择 YZCM 模型，隐藏请求地址输入。请求地址由后端系统配置固定，前端不能自行覆盖。模型标识、能力、启用状态和团队权限均由后端再次校验，未授权请求不得实际发送。

Key 的编辑入口保留在 API 配置主页面的各模型条目下面，沿用当前直接填写 Key 的操作方式。不增加团队默认 Key 独立面板、Key 继承/覆盖选择或常驻右侧配置区。管理员可以为多个模型填写同一个属于本团队 YZCM 钱包的 Key，但编辑某个模型的 Key 不连带覆盖其他模型。成员不重复填 Key，接口也不返回完整 Key。

模型选择不等于协议自动兼容：现有文字、图片、视频、配音适配器继续各司其职。只有能力和实际请求协议已验证的 YZCM 模型可启用；不支持的模型显示原因，不以试错调用消耗用户余额。

### 5.1 API 配置操作与实施顺序（用户最新确认）

本节“自定义预设”指现有的模型展示选择弹窗，不是新增漫画/视频/文本生产参数组合编辑器。

1. 保留 API 配置现有按模型能力分组的结构及“自定义预设”入口。打开弹窗，从后台已保存的 YZCM 允许目录读取对应能力的模型，支持按名称或模型标识搜索，左侧勾选、右侧查看和移除已选模型。
2. 弹窗仅负责选择主页面要展示哪些模型；不填写 Key，不填写或展示请求地址，不在每次搜索时实时请求 YZCM 上游。
3. 点击“确定”后，选中的模型出现在弹窗外的 API 配置主页面；每个模型条目显示名称、模型标识及其下方的 Key 输入框。管理员直接填写 Key，沿用现有自动保存和明确的保存状态反馈，不额外进入配置弹窗。
4. 选择模型本身不代表模型已可调用。对应 Key 成功保存、归属校验通过且模型已适配和获授权后，才进入业务页面对应能力的可用模型下拉。保存失败或 Key 无效时显示原因，不假装生效。
5. 取消勾选只调整主页面展示，不清除已保存 Key，也不擅自改变已有模型可用状态；清空 Key 是单独的明确编辑操作，沿用现有规则从可用下拉移除该配置。再次勾选时恢复已保存配置的脱敏状态。
6. 请求地址统一由后端指定为 YZCM 服务地址；主页面及选择弹窗均无需管理员输入地址。后端仍校验模型、权限和凭据，不能只靠前端隐藏地址字段。
7. 普通成员沿用团队管理员已配置的模型及 Key，仅查看被授权内容，不能编辑凭据或取得明文 Key。平台模型目录同步、适配及开放范围在管理后台维护。

实施时先改模型选择弹窗的目录来源及搜索，再将选择结果接回现有主页面模型条目与 Key 保存流程，随后统一后端地址和权限校验，最后验收业务下拉与真实请求使用同一模型配置。外部历史配置按第 8 节迁移规则处理，不在本次视觉调整中直接删除。

## 6. 团队钱包与个人用量

| 数字 | 数据来源与含义 |
| --- | --- |
| 团队可用余额 | 绑定的 YZCM 消费账号钱包，是实际可消费金额 |
| Key 剩余额度 | 当前 Key 的限制，不等于团队钱包余额 |
| 成员预算 | 一战晟铭内的可选使用上限，不是额外充值或第二次扣费 |
| 实际消费 | YZCM 对应请求的消费日志 |
| 待核账 | 尚未找到匹配消费日志的请求，金额不能显示为免费 |

### 6.1 会员中心：账户、余额与额度

完整的资金和额度信息集中在会员中心。页面顶部突出团队可用余额及“充值”“充值记录”入口；下方展示累计充值、累计实际消费、待核账请求数量和数据更新时间。会员身份、有效期沿用已有会员数据，不用钱包余额推算会员等级或有效期，也不在本次新建会员收费方案。

团队管理员可以查看、设置成员使用额度，展示额度周期、上限、已用、剩余和调整记录。成员预算是使用上限，不移动 YZCM 钱包资金；提高预算不代表充值，收回预算不代表退款。预算与实际扣费分别保存，未知费用请求保持待核账。若某类调用尚未具备可靠的并发额度控制，必须明确说明适用范围，不能宣称已经能够硬性封顶。

普通成员主要看自己的额度、已用和剩余；是否可见团队钱包由管理员权限控制。金额及周期须明确，不能把“本月额度”和“全部历史消费”相减。额度未设置显示“未设置上限”，未知已用或剩余不补成零。团队管理员查看团队与成员明细，所有可见范围由后端限制。

Key 剩余额度放在对应模型凭据配置中，不放在主钱包数字旁冒充团队余额。冻结金额只有 YZCM 返回可靠字段且语义验证通过后才展示；不能将待核账数量换算成虚构冻结金额。

### 6.2 用量与制作：统计、详细账单与制作记录

页面分为三个页签，保留现有入口和主题，会员中心的完整钱包卡不在这里重复铺开：

| 页签 | 主要内容 |
| --- | --- |
| 用量概览 | 今日/本月已核账实际消费、待核账数量、消费趋势、成员和项目统计 |
| 调用账单 | 时间、实际操作成员、作品/项目、功能、模型、用量、实际扣费、核账状态；可展开请求编号 |
| 制作记录 | 小说/作品、生成图片与视频数量、合成及上传结果，链接回对应作品 |

概览和账单支持日期、成员、项目及漫画/视频/文本功能筛选，提供当前权限和筛选范围内的导出。日期口径统一使用系统展示时区；表格分页、统计和导出必须采用相同筛选条件。无权查看的成员与项目不能通过导出或汇总泄露。

制作成功和收费核账是两个独立状态。生成成功但未查到账单显示“制作成功 / 待核账”；调用失败但 YZCM 已收费，保留失败原因和真实费用。生成次数、重试次数、成品数量分别统计，不把一次模型调用直接算成一份制作成品。

统计制作数量只使用已落库的真实产物和任务状态；调用没有关联作品时显示“未关联作品”，不虚构所属。重试保留各次请求账单，但成品统计按产物标识去重。历史无成员归属的费用单列“历史未归属”，不自动平摊给成员。

### 6.3 两页数据一致与现有经验的应用

会员中心与用量页面共用团队绑定、余额查询及核账服务，不各自计算一套金额。实际消费汇总明确统计时间范围及待核账情况；两页刷新后对同一范围的已核账消费必须一致。YZCM 钱包余额还可能受站外调用、充值、退款和调整影响，因此不能用“一战晟铭账单总额”倒推钱包。

此前参考界面中的账户汇总、成员额度管理、按项目/成员查消费用于本方案；其积分转入转出操作不直接照搬到人民币团队钱包。消费趋势、排行与明细都必须由真实数据生成，数据缺失时保留空状态。

余额查询失败显示“暂无法获取”和最近更新时间，不显示为 0；缓存余额注明时间，不宣称绝对实时。并发请求最终是否扣款以 YZCM 为准，不用本地余额缓存承诺一定可调用。不同团队不共用余额缓存或查询凭据。

沿用现有 `yzcmusage` 请求归属与消费日志核账，成员 ID 必须取认证身份，不能由请求参数冒充。账单以对应 YZCM 用户及 Token 范围查询，禁止跨团队读取。重试与补账不重复扣本地费用；失败请求是否收费仍以实际消费日志为准。

充值走 YZCM 已有流程，本次不新建支付通道或自行加减余额。新增充值入口只跳转绑定账号的充值页面；没有验证单点登录前，不宣称跳转即自动登录。

## 7. 模块与保存内容

后端拆分清楚的服务职责：账号绑定/开户、统一密码验证、模型目录、团队凭据、余额查询；继续复用已有请求归属与核账模块。页面层只调用服务，不相互挪用视频/漫画/文本的生产入口。

MySQL 保存绑定、开户任务、目录及启用选择、成员额度策略与调整记录、必要审计信息。任务持久化走现有 MySQL 任务机制；Redis 用于短期缓存、频率控制和并发锁，唯一约束仍在 MySQL 中保证幂等。凭据复用现有受保护的配置存储；不把管理令牌、模型 Key 或密码写入文档及日志。

绑定记录至少包含本地稳定归属 ID、YZCM 用户 ID、来源标识、状态、最近错误码和同步时间；数据库对稳定归属及远端用户建立唯一约束。新迁移号在实施前查重确定，避免复用已有 `8800402`。

按当前代码结构作局部变更，不夹带全仓目录搬迁。Go 提供接口并嵌入 React+Antd 页面，发布单个后端程序；禁止新增 Actions 上传部署。

## 8. 旧配置迁移与上线顺序

先只读盘点已有团队、管理员、模型预设和 Key。记录旧配置的可恢复副本，不在打开页面时自动覆盖。

- 已指向 YZCM 且模型受支持的预设，保留模型与 Key 并映射到新目录。
- 外部地址预设保留为只读历史，标记需迁移；用户确认替换前不偷偷把旧 Key 发往 YZCM。
- 新托管调用路径不得绕过限制继续使用外部地址；旧任务有明确暂停/迁移状态，不自动失败重试收费。
- 共享同一上游消费账号的不同团队不能被当作独立余额验收通过；必须分别开户、配置各自 Key。设置 Key 时验证其属于绑定钱包，无法验证则不允许标记配置完成。
- 新功能按服务能力开关启用；先部署兼容的新 YZCM 服务，再部署一战晟铭，完成两站连通检查后启用。失败可关闭新入口回退，保留已开户账号、余额与审计记录，不能删除钱包作为回滚方式。

交付顺序：本地 4001 真实验收 → GitHub 已确认远端 `cui1112233/yzcm` → 线上。应用使用 `scripts/deploy-go-embedded.ps1`；YZCM 配套服务单独记录提交和回退点。运行 SHA 和健康状态都需核验，文档提交不代表功能上线。

## 9. 验收要求

1. 新建管理员勾选/取消开通均符合预期；开户接口重复、超时、回写失败、并发重试只产生一个绑定账号。
2. 现有管理员无需提供旧密码即可开通；同名冲突和超长用户名明确阻塞，不覆盖他人资产。
3. 两站同名同密码可登录；旧 scrypt 与新 scrypt-v1 账号都通过；改密、找回、停用和验证服务中断行为一致，原生维护账号不受影响。
4. 两个团队分别充值/查询，余额、Key 与消费日志相互隔离；普通成员不能读取他人凭据或团队账单。
