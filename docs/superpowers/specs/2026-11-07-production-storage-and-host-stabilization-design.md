# 生产服务器存储深度清理与 TOS 迁移设计

日期：2026-11-07  
目标服务器：`115.190.156.223`  
应用目录：`/opt/www/qiantie`  
设计原则：先保住数据和回滚能力，再清空间；先验证 TOS 可读，再删本地文件。

## 1. 背景与已确认现状

2026-11-07 线上只读盘点的结果：

- 系统盘共 20GB，已使用约 18GB，剩余约 952MB，使用率 95%。
- `/opt/www/qiantie-artifacts` 共约 3.9GB，其中 1298 张 PNG 约 3.61GB，32 个 MP4 约 187MB。
- 数据库中有 1075 条漫画页图片和 222 条资产图片，两者合计 1297 个不同的本地文件引用。因此这些 PNG 基本都是正式业务数据，不是可随意删除的缓存。
- 线上启用了本地合成，但没有配置合成视频 TOS。数据库中 1123 条合成结果均为本地 `/api/.../merge-media/...` 地址，没有 TOS 或 HTTPS 远程成片。
- 线上只配置了参考图 TOS，没有配置漫画成品图 TOS 和合成视频 TOS。
- 设置页“制作文件保留时长”只管理“作品被删除后的本地合成视频”，不会清理未删除作品，不会清理漫画图片，也不是内存限制。
- 当前本地文件回收队列为空，所以该设置目前不会为现有文件腾出空间。
- `/opt/www/qiantie` 约 2.0GB，保留了 23 个历史二进制；当前运行目标是 `qiantie-202611071612`。
- `/root/backup-20261104` 约 1.7GB，`/root/backup-20261105` 约 510MB，后续两个带完整回滚信息的备份约 69MB 和 70MB。
- APT 缓存和软件列表约 412MB，日志约 292MB，其中 systemd journal 约 85MB。

## 2. 目标

1. 不删任何仍被数据库引用、且未确认已安全迁移的图片或视频。
2. 首轮不碰 3.9GB 业务媒体的前提下，将系统盘使用率从 95% 降到 80% 以下，目标是 75% 左右。
3. 将漫画页图片、书籍资产图片和合成视频的正式存储迁到 TOS，服务器仅保留短期临时文件。
4. 让“制作文件保留时长”的界面说明与真实行为一致，避免用户误以为它会清理全部制作文件。
5. 同时处理已盘点的明显安全问题：HTTP 不强制 HTTPS、3000 端口公网暴露、UFW 未启用、Nginx 版本暴露和系统安全更新积压。

## 3. 不在本次立即范围内的事项

- 不立即禁用 root 密码 SSH；等用户完成 SSH 密钥准备后单独处理。
- 不在首轮将 Qiantie systemd 服务从 root 迁移到专用用户；需先梳理文件权限、FFmpeg 和归档目录。
- 不盲目清理 MySQL binlog；先确认是否有备库/备份依赖，再单独调整保留周期。
- 不升级到 Ubuntu 26.04；只安装当前 Ubuntu 24.04 的安全补丁。
- 不执行“按时间一刀切删图片”。媒体文件必须以数据库引用和 TOS 可读验证为删除条件。

## 4. 分阶段方案

### 阶段 A：立即腾出安全磁盘空间

在任何删除前，先记录当前磁盘、运行二进制、systemd、Nginx、数据库和媒体引用统计。

允许删除的范围：

- 删除 `/root/backup-20261104` 和 `/root/backup-20261105` 中的重复旧二进制、重复数据备份和旧数据包。删除前为目录生成文件清单和 SHA256，并确认后续回滚包完整。
- 保留 `/root/backup-20261106-25` 和 `/root/backup-20261106-26`，以及本次操作前新建的最小化配置/数据库备份。
- `/opt/www/qiantie` 只保留当前运行版、最近 3 个可回滚版本和一个已验证的稳定版。当前运行目标 `qiantie-202611071612` 永远不得被删除。
- 清理 APT 下载缓存，重建软件列表，将 systemd journal 压缩到 7 天或 100MB 以内。
- 只删除超过 30 分钟、名称严格匹配 `qiantie-local-merge-*` 的中断临时目录。

禁止删除的范围：

- `/opt/www/qiantie-artifacts` 中仍被数据库引用的 PNG、JPG、MP3 和 MP4。
- 当前运行二进制、`qiantie` 符号链接、`qiantie.env`、`runtime-release.json`和 systemd 服务文件。
- MySQL 数据文件、Redis 数据、TOS 对象和当前 Nginx 证书。

### 阶段 B：将媒体正式存储迁到 TOS

引入一个统一的媒体存储层，后端根据数据行里的存储类型读取“本地文件”或“TOS 对象”，前端不感知底层差异。

新产生的漫画图片、资产图片和合成视频使用以下两阶段提交：

1. 写入服务器临时文件，计算大小和 SHA256。
2. 上传到 TOS 的独立前缀，例如 `comic/images/`、`comic/assets/` 和 `merge/videos/`。
3. 通过 TOS HEAD/读取验证对象存在、大小一致；必要时核对哈希。
4. 在同一次数据库更新中记录存储类型、TOS object key、文件大小和校验值。
5. 只有数据库更新成功后，本地文件才进入延迟回收队列。
6. 上传或验证失败时保留本地文件，指数退避重试，不允许先删后传。

存量文件迁移采用小批次、可续传方式：

- 每批最多 50 个对象，只并发 2 个上传，避免再次将 TOS 出口和 Go 服务拖死。
- 每个对象有 `pending/uploading/verified/committed/cleanup_pending/cleaned/failed` 状态，重启后只继续未完成项，不重复上传已验证项。
- 先迁移一个测试作品，在线验证图片预览、原图、合集下载和合成视频；通过后才扩大。
- 存量本地文件延迟 24 小时删除，期间仍可快速回滚到本地存储。

TOS 配置必须使用独立环境变量，不在前端、Git 或日志中记录凭证。可以复用现有 TOS 账号，但应使用独立 bucket 或至少独立前缀和最小权限策略。

### 阶段 C：重新定义“制作文件保留时长”

设置页保留 3/7/14/30 天选项，但文案和后端行为调整为：

- 对 TOS 作为正式存储的新数据：本地临时副本在 TOS 验证成功后 24 小时自动清理，不受 3/7/14/30 天选项影响。
- 对作品本身：3/7/14/30 天只决定“删除作品后的可恢复保留期”，期满才清理相应 TOS 对象。
- 设置页明确显示“这是硬盘/对象存储保留策略，不是运行内存限制”。
- 提供存储统计：本地使用量、TOS 使用量、待迁移数、待回收数和最近错误。

### 阶段 D：服务器暴露面收紧

1. 备份 Nginx 配置并通过 `nginx -t`。
2. 80 端口只返回到同路径 HTTPS 的 301/308 跳转。
3. 3000 端口改为只监听 `127.0.0.1` 或取消该公网 server block，保留内部调试能力。
4. 启用 UFW 前先明确放行 22/80/443，保留当前 SSH 会话，用第二个 SSH 会话验证后再结束首个会话。
5. 关闭 Nginx 版本暴露，增加 `X-Content-Type-Options` 和安全的 `Referrer-Policy`。CSP 和带 `includeSubDomains` 的 HSTS 延后，避免直接影响现有 React/外部资源。
6. 隐藏或限制 `/api/runtime-build-info` 中不必要的路径和版本细节，但保留运维所需的简化版本标识。

### 阶段 E：系统安全更新

- 在磁盘空间恢复、配置和数据备份完成后，刷新 APT 索引并仅安装 Ubuntu 24.04 安全更新。
- 检查 `needrestart` 和 `/var/run/reboot-required`。如需重启，预留 1–3 分钟维护窗口。
- 重启后验证 MySQL、Redis、Nginx 和 Qiantie 自动启动，再进行页面和 API 冒烟验证。

## 5. 执行顺序与停止条件

执行顺序固定为：

1. 基线记录与备份。
2. 阶段 A 安全清理。
3. 磁盘、服务和线上页面验证。
4. 阶段 D 网络收紧并验证。
5. 阶段 E 安全更新并验证。
6. 本地完成阶段 B/C 的代码、单元测试、嵌入式前端构建和本地浏览器验收。
7. 发布新二进制，先迁移一个测试作品，再分批迁移全部存量媒体。
8. 24 小时观察无误后，开始删除已迁移且可读的本地媒体。

任意一条命中时立即停止：

- 备份失败、校验值不一致或回滚二进制不可用。
- 空间不足 1GB 且找不到已确认安全的清理对象。
- `nginx -t` 失败或新 Nginx 配置导致 HTTPS/健康检查异常。
- 启用 UFW 后第二个 SSH 会话无法建立。
- TOS 上传后的 HEAD/读取验证失败，或文件大小/校验值不一致。
- 迁移后的浏览器预览、原图、合集下载或合成视频任一失效。
- 更新前的服务健康检查未通过。

## 6. 回滚设计

- 清理前记录被删文件清单、大小和 SHA256。保留当前版、最近 3 个版本和一个已验证稳定版。
- Nginx 和 UFW 改动前保留带时间戳的配置副本；验证失败时原子恢复并 reload。
- TOS 迁移在 24 小时观察期内保留本地文件和原存储引用；回滚只需切回本地存储。
- 应用发布仍使用单个 Go embed 二进制；新版失败时将 `qiantie` 符号链接指回已验证版本并重启服务。
- 系统包安全更新不保证可完全逆向卸载，所以必须放在空间恢复、数据备份和应用回滚能力完成之后。

## 7. 验收标准

阶段 A/D/E 完成标准：

- 系统盘使用率低于 80%，目标不高于 75%。
- Qiantie、Nginx、MySQL 和 Redis 状态正常，无 OOM、文件系统或 I/O 错误。
- `http://yzcm.site/...` 跳转到同路径 HTTPS，`https://yzcm.site/` 和 `/health` 正常。
- 公网 3000 端口无法访问，22/80/443 保持可用，MySQL、Redis 和 Go 4000 仍只监听本机。
- 已登录用户能打开批量工厂、设置页、漫画图片和合成视频。

阶段 B/C 完成标准：

- 新图片和新合成视频均存入 TOS，数据库不再新增长期本地媒体引用。
- 存量 1297 个被引用图片按批迁移，每个对象都有可审计状态，重试不会重头上传已完成对象。
- TOS 迁移后的预览、原图、下载、合集、合成和发布链路全部通过。
- 只有状态为 `committed/cleanup_pending` 且超过 24 小时观察期的本地文件会被删除。
- 设置页能正确解释本地临时缓存与删除作品保留期的区别，并展示实际存储用量。

## 8. 预期影响

- 阶段 A 预计可释放约 4GB，不影响现有图片和视频。
- 阶段 D 仅需 Nginx reload，正常情况无感。
- 阶段 E 如需重启，预计停机 1–3 分钟。
- 阶段 B 在迁移期间会增加 TOS 流量和少量 CPU/I/O，因此采用低并发、可续传和随时暂停的批处理。
