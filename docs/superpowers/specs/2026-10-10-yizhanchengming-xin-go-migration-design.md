# 一战晟铭新主线 Go 化迁移设计

日期：2026-10-10

## 目标

以 `https://github.com/cui1112233/yizhanchengming-xin/` 作为目标架构参考，把当前 V88 中已经可用的页面和业务能力逐步迁移到统一的 Go + React 结构：

- Go 负责 API、任务、Worker、Provider 和发布服务。
- React + Ant Design 负责用户前台和管理后台。
- MySQL 保存账号、业务数据、任务状态和配置版本。
- Redis 只负责队列、延迟任务、分布式锁和短期运行状态。
- TOS 保存图片、视频等长期媒体文件。
- Node/npm 只保留为前端开发和打包工具，不作为正式业务服务。

## 当前问题

当前 V88 仍是混合运行：Node `server.js` 负责页面、登录、部分业务接口和 Go 代理；Go 只负责部分 API。这样会出现 Node 找不到 Go、端口不一致、同一业务有两套事实来源等问题。

## 目标结构

```text
React 用户前台 / React 管理后台
                ↓
             Go API
        ↙       ↓       ↘
     MySQL    Redis      TOS
  业务事实   队列/锁    图片/视频
```

浏览器不直接接触数据库、Redis、TOS 密钥或 Provider 密钥。

## 迁移原则

1. 新仓库是结构参考，当前 V88 是功能和行为参考。
2. 不直接复制旧 Node 文件；保留用户看得见的功能和规则，用 Go 重写后端实现。
3. 每次只迁一个模块，迁完同时补测试和本地页面验收。
4. MySQL 是最终事实来源；Redis 不保存长期业务状态。
5. 旧 Node 代理只作为过渡适配层，不能继续作为新主线业务后端。
6. 不迁移或提交密码、Cookie、Token、API Key 等敏感信息。

## 迁移顺序

### 第一阶段：运行骨架

- 确认新主线的 Go API 启动方式、MySQL 连接、Redis 连接和健康检查。
- 确认 React 前台、管理后台能够分别构建。
- 先让一个 Go 服务能提供 API 和前端静态文件。

### 第二阶段：账号与设置

- 迁移登录、账号、团队、权限、个人中心和设置。
- 账号、权限、配置写入 MySQL。
- 清除 Node 内存账号和文件型事实来源。

### 第三阶段：小说获取与水货生产

- 迁移小说获取、书籍、批量项目、运行记录。
- `/shuihuo-production` 使用 Go API 读取 MySQL。
- 失败、重试、状态恢复由 Go + MySQL + Redis 负责。

### 第四阶段：剧本、提示词和视频

- 迁移 Director、Hook、最终提示词编译。
- 系统提示词只保存在后端，前端不硬编码密钥或系统提示词。
- 视频 Provider、执行器、合并和媒体访问统一由 Go 管理。

### 第五阶段：收口

- React 静态文件由 Go `embed` 打包。
- 停止本地正式 Node 服务。
- 删除已经没有调用方的 Node 业务路由和代理。
- 用真实浏览器流程验证登录、创建项目、执行、失败重试和媒体读取。

## 暂不做的事情

- 不把 React 页面重写成 Go 模板。
- 不一次性复制整个旧 V88。
- 不直接覆盖当前未提交文件。
- 不把公网/ECS 测试结果当成本地迁移完成证据。
- 不在没有真实凭据时伪造 Provider、TOS 或视频成功结果。

## 完成标准

每个模块必须同时满足：

- Go API 测试通过。
- 前台和后台构建通过。
- MySQL/Redis/TOS 的职责边界清楚。
- 本地浏览器流程真实可走通。
- 旧 Node 接口不再是该模块的事实来源。
