# G11 资产检查实施与对照记录

本项已有实现和受控对照，尚未通过完整原版页面与真实供应商验收。完整复刻目标及36组清单保持不变。

## 已核对并实现

- 原版前端 `index-DszfAkKD.js` 可读恢复稿444593–444699：关闭只隐藏，取消为独立操作；检查结果先确认，才新增资产。CM新增独立检查弹窗，切页关闭不取消，顶栏恢复同一任务进度，默认全选有内容分集。
- 原生无网回放和六对客户端最终请求见 `07-parity-execution/asset-check-original/captured-client-requests/catalog.json`、`native-orchestration-replay.json`。批量检查实际用 PARSE_V2 system 加补充 user，不是 COMPLETE_CHECK；通用/海外三类分别逐字节对照，后端 prompt 模块独立构造，使用项目自己的模型。
- 最多3集并行，每集人物、场景、道具3类并行。取消停止新集，已经开始的集继续收集结果。先完成集的新名称优先；同类型名称trim后精确区分大小写，已有资产优先，不覆盖。
- MySQL保存冻结输入、每步最终请求、原始回包、候选、取消标记及应用状态；Redis提供到期队列与项目租约。只有明确确认添加才在一个事务内新增资产并记录已应用。显式不添加持久化，窗口X关闭保留候选。
- 查阅、生成/取消、编辑/入库权限分别检查；写操作取锁后再次检查权限。接口只回公开摘要，不泄漏系统提示词、源正文、原始模型回包或租约。

## 明确的独立可靠性修复

原版非法JSON会误报空成功，CM记录失败并显示对应分集，不伪装无遗漏。原版未观察到任务ID/状态轮询或应用重启恢复接口，CM的MySQL/Redis持久任务是独立实现，不宣称恢复了原版原生持久机制。

已发出但结果未知的请求不自动重发；明确结束本次检查后，可确认已收到的候选并新开检查。恢复已收到回包仅重新解析，不再请求模型。启动回包丢失后按请求标识取回冻结任务，即使当前原文/资产有变化也不重新提交。旧租约的晚到回包无法覆盖新状态。
