## 本轮结果与证据等级

### 1. 普通分集标题没有被识别（已复现）

- 输入：`第1集 开场\n1-1 操场\n正文甲\n第2集 转折\n2-1 教室\n正文乙`。
- 调用当前真实导出函数 `comicScriptEpisodes`，结果只有 `[1]`；同一文本给两处标题加上 `# `，结果为 `[1,2]`。通过Node直接加载当前模块执行，无模型调用。
- 入口：`frontend/src/user/pages/ComicScreenplayStoryStage.jsx:17-20`，导入TXT/MD直接读取并保存内容，显示数量使用同一函数（第7、25行）。
- 规则：`frontend/src/user/pages/comic-screenplay-stages.js:10-11` 只识别带井号的阿拉伯数字集标题；页面自己的分集函数也如此，见 `ComicScreenplayPage.jsx:35-40`。
- 后续：`backend/internal/screenplay/storyboard_service.go:366-368,382-386` 同样要求井号，无法识别就把整份文档作为第一集。说明问题可能传到分镜输入，不能仅修页面数量。
- 原版对照：用户给出的原版格式提示使用“第1集 / 1-1 场景1”。本轮未执行原版解析器，因此不声称原版所有格式的解析行为已验证。
- 建议：前后端采用同一套明确格式规则，接受带/不带井号标题；未识别时明确展示“按单集导入”并允许检查拆分结果。重复集号、空集、中文数字、开场说明需分别规定，不能静默合并或吞文字。

### 2. 人物名称包含关系会错误收集参考图（源码确定，未跑真实出图）

- `backend/internal/httpapi/screenplay_media_workbench.go:821-836`：把人物、场景、道具的文本分别对所有资产名字做 `strings.Contains`，匹配后加入参考目标，再读取这些目标的已选图片。
- 示例：分镜只写“林晚晴”，资产有“林晚”和“林晚晴”，两个名字都满足判断。本轮复算该判断得到两个匹配，不等于执行了整个媒体服务或供应商出图。
- 建议：以资产ID绑定；旧文本按明确分隔符和完整名称匹配，歧义让用户确认，按人物/场景/道具类型各自匹配。不能以长名字优先掩盖真实同时出现两个人物的情况。
- 验收：同名前缀、同名不同类型、重命名、删除资产、无已选图、同图去重；没有精确匹配时不能偷偷采用相似名字的图片。

### 3. 图片/配音重试可能重复提交（源码风险，待模拟响应丢失验证）

- `frontend/src/user/pages/ComicScreenplayMediaPanel.jsx:36` 每次点击图片/配音操作都新建请求标识；失败后解除按钮忙碌状态。
- `backend/internal/httpapi/screenplay_media_workbench.go:662-685` 依据该标识识别已有请求；新标识不能复用旧结果。
- 如果服务端已提交但响应中断，用户重试会产生新标识。尚未实际制造断网或验证供应商计费，不能称已发生重复扣费。
- 建议：同一次输入保持请求标识，先查询原请求状态；只有明确失败且用户确认重新生成，才创建新请求。状态区分“未提交 / 执行中 / 结果待确认 / 已完成 / 明确失败”。

### 4. 刷新可能覆盖正在编辑的原文（源码风险，待界面复现）

- `frontend/src/user/pages/ComicScreenplayPage.jsx:209-227`：同项目刷新也无条件把服务端原文写回 `source`；`persistSource:229-238` 另行异步保存，未见该刷新处检查本地原文是否已改动。
- 原文输入仍可编辑，见同文件第582行；任务收尾也走刷新。存在本地修改与旧读取结果交错的风险。

## 设计与流程对照

主路径应保持：项目库 → 剧本 → 资产 → 分镜 → 媒体制作与交付。配置统一从自己的模型服务读取，预设提示词仍在后端prompt模块维护；前端选择只传标识和允许编辑的用户配置。选择项数量一致不代表最终生成使用了相同模板，验收需检查保存、重开、请求构造和结果解释。

现页面既有三阶段，也保留“原文与剧本工具”等抽屉。不能因为旧工具存在就认定假功能，但重复入口、不同选项表达容易让用户不清楚哪一份配置生效。应让旧入口复用同一份项目配置和操作，保留兼容数据，避免继续维护两套状态。

已排除的一项误判：资产阶段的下一步并非无条件无提示跳过。`ComicScreenplayPage.jsx:638-644` 会读取媒体，缺图时列出缺失资产并要求确认，读取失败会提示错误。它仍需原版同状态对照，但不是本轮已确认缺陷。

## 三种处理方式

1. **推荐：先保证内容和任务正确，再逐页对齐。** 先分集、参考绑定、重试与草稿保护；再分类和重复入口；最后逐项核对尺寸、图标、布局与状态。修复范围小，能保留已有功能；每项按正常、空值、重复、错误、取消、重开分别对照。
2. **先改外观。** 用户能更早看到布局接近原版，但错误分集和参考图会继续传到生成，不适合当前优先级。
3. **整体重写。** 可以整理结构，但容易回退已经验证的上传、音频、版本和权限链，成本与回归风险最高，不建议。
