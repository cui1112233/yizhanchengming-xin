# 短篇正文修订对话合同

来源：原版novels.pyd SHA256 b5b22086c64851e0e94fc70a509cddbaf4ec144ac5beedc64e3a9a8caa40e57d；已归档原生调用证据见 `docs/verification/novel-resume-evidence-20261120/FINDINGS.md` 第4节，`0x180165140.assembly.txt:2852–2977,3010–3146`。本轮补充取证保存在 `docs/verification/novel-short-recovery-20261120/`。

## 原版已经确认的规则

正文修订以writer身份进行，顺序是system(writer_sys)、user(原首稿写作请求)、assistant(draft_v1.raw_content.strip)、user(根据审稿意见写第二版的跟进要求)。第一条system仍经过仿写writer附加约束包装。

这里的draft_v1是补写合并并重新解析后的完整首稿，而不是最初缺章节的回复。原版这条可见路径执行一次第二版修订，不能据此称原版使用CM当前的多轮评分循环。

## CM实现合同

| 项目 | 要求 |
| --- | --- |
| 输入 | 本段实际冻结并发送的首稿system/user、有效首稿原始回复、本轮审核资料、后台冻结的修订预设、用户思考要求 |
| 输出 | 模型实际收到四条消息；现有JSON正文结构通过校验后进入后续审核及保存；messages参与持久化调用指纹并保留可核对元数据 |
| 历史边界 | 仅新建短篇仿写任务冻结short_writer_conversation_version=1；旧任务无此字段时请求和重试指纹不变 |
| 首稿边界 | 每段单独保存上下文；原始回复可由成功的JSON格式修复得到；后续修订不得覆盖这份有效首稿。任务重试从成功调用日志重建，不重新生成首稿 |
| 修订边界 | 第一条保持原writer system及仿写约束；最后一条user必须实际使用冻结的修订预设和审核输入，不能丢掉后台配置 |
| 格式错误 | 四消息修订回复格式无效时，保留原四消息，再追加坏回复和格式修复要求；最多沿用现有一次格式修复，不降级为无历史的两消息请求 |
| 失败 | 首稿上下文缺失时明确失败；取消后不新增请求；429等临时失败不重写已完成首稿；结果不明仍遵守原确认/暂停保护 |
| 账号与配置 | 沿用当前账号已授权模型及阶段配置、原任务冻结预设；模型不可用明确失败，不静默换通道 |

## 不能混称一致的地方

CM当前仍按章分段生成JSON，而原版一次生成全篇带标记的Markdown。CM可配置多轮评分修订，而本条原版短篇路径只执行一次第二版修订。本轮只恢复四消息的上下文关系，不宣称全篇生成、缺章解析、修订次数和提示词动态builder全部相同。

原版空章节补写须单独分析章节解析、缺失判定、次数和拼接规则；当前JSON结构修复不能冒称该功能已对齐。修改后重新终审入口同样须先有证据，本轮不自行添加入口。
