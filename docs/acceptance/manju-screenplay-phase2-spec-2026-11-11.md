# 漫剧创作（`/comic-screenplay`）第二阶段需求规格

- 日期：2026-11-11
- 口径：用户已确认**口径一（A）**——`/comic-screenplay` 是“漫剧创作”的正门，对标洛水「剧本创作」；`/batch-factory` 只作为生产基础设施复用，不作为要模仿的产品形态。
- 性质：只读盘点后的需求规格。**本文不包含任何代码改动**；未构建、未重启 4001、未调用生成接口、未消耗额度。
- 写法：正文用白话；括号里放文件名、行号、接口名；洛水侧放 bundle 字符偏移或截图文件名。完整索引见第 10 节。
- 现状基线：2026-11-11 的 `v88` 工作区。

---

## 0. 一页结论

1. 四步骨架已经存在，但只有前三步是“真跑”的：上传原文→生成剧本→提取资产→生成分镜词，这四件事都调用了用户自己配置的文本模型，并把结果写进 MySQL。
2. 第四步「生产与导出」目前是**状态壳**：点“启动生产任务”只会创建 9 条步骤记录，全部停在 `pending`；仓库里没有任何运行时执行器去推进它们（`NextUnit(` 只出现在 `*_test.go`，[state.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/screenplay/state.go#L133)）。
3. 第三步到第四步之间缺“一台发动机”，可以拆成六环：出图、出视频、配音、上字幕、合音频、合成片。V88 在 `/batch-factory` 里已经有 TTS、ffmpeg 合并、视频通道等零件，但都绑在“水货生产”的书/批次模型上，**不能直接插到漫剧工作台**，需要抽一层通用任务与素材存储。
4. 在动这台发动机之前，有三件“界面事实”必须先修，否则用户会误以为数据丢了：
   - 工作台右侧「项目设置」改了不保存（前端没有调用更新项目接口）；
   - 上传/粘贴的原文不落库，刷新页面就没了；
   - 「生成 CM 分镜」把整篇剧本当成第 1 集一次生成，没有“按集生成”。
5. 第一批建议只做“纯界面 + 已有接口 + 已有能力复用”的五件事，详见第 9 节；在用户确认前不改代码。

## 1. 对齐基线

### 1.1 洛水的三个主页签 vs V88 的四个页签

洛水项目内是 3 个固定主页签，顺序为 **剧本 → 资产 → 分镜**（bundle 偏移 33913600 附近的 `Sd = [{key:"story",label:"剧本"},{key:"assets",label:"资产"},{key:"storyboard",label:"分镜"}]`）。每个页签有完成态文案：`剧本内容整理完毕 / 资产设定已确认 / 分镜内容已确认`（偏移 33914255、33914285、33914318），意思是“上一步确认了才进下一步”。

V88 是 4 个页签：`原文与剧本 / 资产库 / 分镜工作台 / 生产与导出`（[ComicScreenplayPage.jsx](file:///f:/脚本测试/一战晟铭-v88/frontend/src/user/pages/ComicScreenplayPage.jsx#L208-L228)）。左侧四步导航文案是 `1. 剧本 / 2. 资产 / 3. 分镜 / 4. 生产`（同文件 201–205 行）。

对齐后的映射：

| 洛水 | V88 | 是否已对齐 | 说明 |
|---|---|---|---|
| 剧本（含 AI 生剧本、医生、版本、导入） | 原文与剧本 | 部分 | V88 有生成/编辑，没有医生、版本文档对比、爆款开头 |
| 资产（角色/场景/道具、参考图、音色） | 资产库 | 部分 | V88 有抽取/编辑，没有参考图、没有音色试听 |
| 分镜（规划→分镜词） | 分镜工作台 | 部分 | V88 只有“一步出词”，没有“先规划再写词”，也没有按集 |
| 分镜页签内的 生图/视频/配音/字幕/合并 | 生产与导出 | **未对齐** | V88 第四步只有 9 步状态和 JSON 导出 |

### 1.2 页面的“四步”和后台的“九步”不是一回事

V88 的九步批次定义在 [state.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/screenplay/state.go#L22-L32)：

```
0_ingest 整理原文
1_screenplay 生成剧本
2_screenplay_doctor 剧本审核
3_assets 资产提取
4_preset_doctor 预设质检
5_storyboard 按集分镜
6_storyboard_doctor 分镜审核
7_video 批量出视频（依赖外部能力）
8_finalize 收尾编号
```

页面的四步只是把九步“折叠”展示：剧本=0/1/2，资产=3/4，分镜=5/6，生产=7/8。**今天页面上能点的按钮并不走这九步**，九步只是数据库里的记录。规格里必须把“页面动作”和“批次动作”分开写，不能再用九步状态冒充生产进度。

## 2. 跨四步的通用规则

这一节先定公共规则，后面每一步不再重复。

### 2.1 提示出现在哪

- 现状：所有错误都用 antd 的 `message.error`，出现在页面顶部居中，约 3 秒消失；成功用 `message.success`。见 [ComicScreenplayPage.jsx](file:///f:/脚本测试/一战晟铭-v88/frontend/src/user/pages/ComicScreenplayPage.jsx#L46-L121) 的 `refreshProjects / openProject / submitCreate / runTask` 等函数。
- 现状：网络类失败还会触发全局 `qiantie:api-error` 事件（[client.js](file:///f:/脚本测试/一战晟铭-v88/frontend/src/shared/api/client.js#L37-L48)），可能出现“顶部 toast + 全局提示”两条。
- 规格目标：
  1. 字段级错误（空、超长、格式不对）必须**贴在字段下方**，不能只弹顶部 toast；
  2. 任务级错误（模型失败、取消、断线）用顶部 toast，并且**保留在页面上直到用户关闭或重试**，不能 3 秒消失；
  3. 同一个错误只提示一次，禁止“toast + 全局横幅”重复。

### 2.2 长任务、取消、断线

- 现状：生成剧本、提取资产、生成分镜都传 `timeoutMs: 0`，即**前端不设超时**，由用户点“取消任务”触发 `AbortController`（[comicScreenplay.js](file:///f:/脚本测试/一战晟铭-v88/frontend/src/shared/api/comicScreenplay.js#L81-L109)；页面 44、92–98、196 行）。
- 现状：用户主动取消时，前端抛出 `AbortError`，`runTask` 直接吞掉，**页面没有任何“已取消”提示**（页面 96 行）。
- 现状：服务端收到取消会返回 499 和 `用户取消了推理`（[screenplay_routes.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/httpapi/screenplay_routes.go#L573-L588)）；但如果是浏览器先断开，服务端只是 context 取消，前端已经不在，结果不会落库。
- 规格目标：
  1. 取消后必须提示“已取消，本次生成的内容不会保存”，并恢复按钮；
  2. 断线后重新进入项目，必须能看到“上次任务未完成”的标记和重试入口；
  3. 任何长任务都必须有服务端任务 ID，允许刷新后继续查询，不能只靠浏览器内存。

### 2.3 重复点击与幂等

- 现状：`runTask` 有 `if (working) return`，同一时间只允许一个任务（页面 92–93 行）；但 `startBatch / pauseBatch` 没有这个判断，只靠按钮 loading（页面 100–110 行）。
- 现状：创建项目没有服务端幂等键；同名项目可以创建多个。
- 规格目标：
  1. 所有“会花钱”的按钮（生成剧本/提取资产/生成分镜/试听配音/生成图片/生成视频）都必须在服务端带幂等键，重复提交返回同一个任务，不重复计费；
  2. 按钮在任务期间必须真正禁用，而不只是显示 loading；
  3. 重复提取同一批资产时，按“类型 + 名称”覆盖，不新增重复行（现有唯一键已支持，见 [screenplay_schema.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/storage/screenplay_schema.go#L155-L177)）。

### 2.4 数据落在哪

| 数据 | 现状落点 | 依据 |
|---|---|---|
| 项目配置 | `screenplay_projects`（含后加的 `model_id / prompt_id / asset_degree / permission_mode`） | [screenplay_schema.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/storage/screenplay_schema.go#L16-L33)、[同文件 324 行起](file:///f:/脚本测试/一战晟铭-v88/backend/internal/storage/screenplay_schema.go#L324) |
| 剧本 | `screenplay_documents`（多版本，有 active 标记） | 同文件 34 行起 |
| 场次 | `screenplay_shots` | 同文件 53 行起 |
| 角色/场景/道具 | `screenplay_characters / scenes / props` | 同文件 71/86/101 行起 |
| 资产（统一视图） | `screenplay_assets` | 同文件 155 行起 |
| 分镜 | `screenplay_storyboards` + `screenplay_storyboard_shots` | 同文件 178/193 行起 |
| 批次 | `screenplay_batches / batch_steps / batch_episodes / batch_logs` | 同文件 216 行起 |
| 媒体（图/视频/音频/字幕/成片） | **没有表** | 全仓没有对应 schema；第四步只导出 JSON |

规格目标：新增媒体任务与素材落点（建议 `screenplay_media_jobs` + `screenplay_artifacts`），每个镜头一行任务，记录 provider、状态、重试次数、产物地址、错误原文。这样刷新、暂停、断线都能恢复。

### 2.5 当前必须先修的三个“界面事实”

这三条不是新功能，是现有页面会误导用户的地方，建议放进第一批。

1. **项目设置不保存**：右侧「文本模型 / 画面比例 / 创作模式」只改 React state（页面 230 行），没有调用 `PATCH /api/comic-screenplays/projects/{id}`。用户改完以为生效，重新进入又变回去。
2. **原文不落库**：上传或粘贴的原文只存在 `source` state（页面 34、69、209 行）；`source/parse` 只返回文本，不写库（[screenplay_routes.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/httpapi/screenplay_routes.go#L291-L331)）。刷新后原文消失，只剩已生成的剧本。
3. **分镜没有按集**：页面把整篇 `document.content` 作为 `content` 发给后端（页面 214 行），后端 `resolveEpisodes` 看到 `Content` 非空就直接当成第 1 集（[storyboard_service.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/screenplay/storyboard_service.go#L197-L239)）。所以“逐集生成镜头组”这句导航文案目前名不副实。

## 3. 第一步：剧本（页签「原文与剧本」）

**一句话：把小说原文交给模型，改写成能拍的分集剧本，并解析出集和场次。**

### 3.1 页面结构

- 左边「原文」：大文本框 + 上传 TXT/DOCX 按钮 + 「生成分集剧本」按钮。
- 右边「当前剧本 · vN」：只读展示生成结果（`<pre>`），没有编辑框、没有版本切换。
- 创建项目时还要填：作品名称、选择模型、选择提示词、选择风格、剧本比例、资产解析程度、上传剧本。
- 依据：页面 209 行、268–277 行。

### 3.2 输入

| 字段（界面文案） | 来源 | 必填 | 上限/约束 | 现状 | 依据 |
|---|---|---|---|---|---|
| 作品名称 | 创建弹窗 | 是 | 前端 `maxLength=80`；服务端只校验非空 | API 封装层会拦空标题，但错误只弹顶部 toast，字段下方没有提示 | 页面 270 行；`comicScreenplay.js` 36–41；路由 107 行 |
| 选择模型 | 创建弹窗 / 工作台右侧 | 是 | 来自 `listAvailableModels('text')` | 创建时按钮在无模型时不可用；工作台里是自由输入框，可以填不存在的模型 | 页面 63、271、230 行 |
| 选择提示词 | 创建弹窗 | 是 | 内置两个：`b_director_screenplay`（专业剧本）、`a1_novel_to_screenplay`（小说转剧本） | 有；提示词决定 `scriptMode` | 路由 73–78；页面 272 行 |
| 选择风格 | 创建弹窗 | 是 | 6 个固定选项（通用动漫/国风3D/写实影视/日系漫画/水墨国风/赛博朋克） | `submitCreate` 里校验 | 页面 15、82、278 行 |
| 剧本比例 | 创建弹窗 | 是 | 9:16 / 16:9 / 1:1 / 4:3，默认 9:16 | 有 | 页面 8、273 行 |
| 资产解析程度 | 创建弹窗 / 资产页 | 是 | `master / master_real / more_diff / standard` | 创建时只记到项目；第二步真正使用 | 页面 9–14、274 行 |
| 上传剧本 | 创建弹窗 | 是 | `.txt` / `.docx`；FormData 上限 24MB，实际读取 20MB | 有；创建后立即调 `source/parse` | 路由 296–310；页面 275 行 |
| 原文 | 文本框 / 上传解析结果 | 生成时必填 | 服务端单次硬上限 **60 万字**；前端不检查 | 有；但**不落库**，刷新即丢 | 服务 14–15、194–215；页面 34、209 行 |
| 创作模式 | 工作台右侧 | 是 | `a1`（小说转剧本）/ `b`（导演级剧本） | 有；但右侧改动不保存 | 页面 230 行；路由 276–284 |

**规格补充：**

1. 创建弹窗必须在前端先校验“作品名称非空”，错误贴在输入框下方，文案“请输入作品名称”（对齐洛水偏移 7990335）。
2. 模型下拉必须只显示“已配置且可用”的文本模型；工作台右侧改成同样的下拉，不允许自由输入不存在的模型。
3. 原文必须落库：建议在 `screenplay_projects` 增加 `source_text LONGTEXT` 或单独 `screenplay_sources` 表；进入项目时回填。否则用户刷新/换设备就丢原文。
4. 原文超过 60 万字时，前端在输入框下方提示“原文超过 60 万字，请按章拆分后分批提交”，不要等点了生成才报错。
5. 长篇小说必须支持“按章/按集分段生成”。洛水是“选章节 → 填参考原文 → 分集创作”（bundle 偏移 2855683 附近的说明），V88 目前只有 `Segments` 接口参数，前端从不传，等于没做。

### 3.3 输出

| 产物 | 存到哪 | 下一步怎么用 | 现状 |
|---|---|---|---|
| 分集剧本正文 | `screenplay_documents`，每次生成新增一个版本，并设为 active | 资产提取、分镜生成都优先读 active document | 有；但页面只显示当前版本，没有版本列表/对比 |
| 场次 | `screenplay_shots`（按 `# 第N集` 标题解析） | 分镜工作台左侧“场次卡片”读的是这张表 | 有；生成后自动解析 |
| 角色/场景 | `screenplay_characters / scenes`（从剧本里粗解析） | 资产页会再单独抽取一次 | 有；两套数据容易重复 |
| 版本号 | `documents.version` | 页面右上角“当前剧本 · vN” | 有；`workspace` 返回文档列表，但页面只用了 active |

规格目标：

1. 生成成功后必须显示“本次生成 N 集 / M 个场次 / 用时 X 秒”，不能只弹“处理完成”。
2. 必须提供版本列表：可查看、可切换 active、可对比（洛水有“文稿对比/版本”，bundle 偏移 2736891、2736983）。第一版可以只做“查看 + 切换”，对比放后面。
3. 剧本正文必须可编辑并保存。洛水页签是编辑器（有查找替换、导入覆盖，偏移 2739749），V88 现在是 `<pre>` 只读。**当前没有保存文档的接口**（`PATCH .../document` 不存在，前端也没有对应函数），第一版需要新增一个“覆盖保存当前剧本”的接口，并做 revision 冲突提示。

### 3.4 边界处理

| 场景 | 现状 | 规格目标 |
|---|---|---|
| 原文为空 | 前端 `请先上传或输入原文`（`comicScreenplay.js` 83 行） | 保留；同时输入框标红 |
| 原文只有空白 | 服务端 `内容不能为空`（`generator.go` 23 行） | 保留；提示“原文不能为空” |

| 上传格式不对 | `仅支持 TXT 或 DOCX 文件`（路由 319 行） | 保留；上传前按扩展名拦截 |
| DOCX 损坏/无正文 | `DOCX 文件已损坏` / `DOCX 中没有找到正文` / `DOCX 正文读取失败` / `DOCX 正文解析失败`（路由 531–570） | 保留；把具体原因展示在文件下方 |
| 文件超 20MB | `文件过大或上传格式无效`（路由 296–298） | 改成明确文案“文件超过 20MB，请拆分后上传” |

| 模型失败 | `API Key未配置，请在全局设置中配置` / `API请求失败: HTTP...`（`generator.go` 18–19） | 保留原文；在按钮下方给“去配置模型”链接 |

| 生成中断线/刷新 | 请求丢失，页面回到项目库；已生成部分不落库 | 任务 ID + 断点续查；未完成时在项目卡片上显示“未完成”标记 |
| 切换项目/返回项目库 | 页面 193 行会 `abort()` 当前任务 | 保留；但要提示“任务已取消” |

## 7. 第三步到第四步之间缺的那台发动机

### 7.1 全景

```
分镜词（已有）
   │
   ├─① 出图：每个镜头组 1 张关键帧/参考图
   │        └─ 需要：图片模型、提示词拼装、参考图、审核失败重试、素材存储
   ├─② 出视频：图片 + video_desc + 时长 → 5–15 秒片段
   │        └─ 需要：视频模型、首帧图、轮询、失败重试、片段存储
   ├─③ 配音：每个角色每句台词 → 一条音频
   │        └─ 需要：台词字段、音色、情绪、TTS、时长测量
   ├─④ 字幕：音频/视频 → 时间轴字幕
   │        └─ 需要：ASR 或 TTS 时间戳、与台词对齐、SRT/ASS
   ├─⑤ 合音频：多条配音 → 一条带气口的音轨
   │        └─ 需要：按镜头顺序拼接、静音补齐、BGM 混音
   └─⑥ 合成片：多段视频 + 音轨 → 成片
            └─ 需要：统一分辨率/帧率、补黑场/静音、封面、上传/下载
```

### 7.2 六环逐条

#### ① 出图

- **一句话**：给每个镜头组画一张“能当视频首帧”的图。
- **洛水怎么做**：分镜页签内的「生图」子页签（偏移 14956799），支持单条生成和「批量生图」（偏移 14684014）；资产图会作为参考图；引擎包括即梦画布、小云雀 CLI、Seedream、nano-banana 等（偏移 2701828、2701953、2709773）。
- **V88 现成能力**：
  - 图片生成主函数 `generateShuihuoImageArtifact`（[shuihuo_projects.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/httpapi/shuihuo_projects.go#L3602)），支持参考图、内容审核、去敏、缓存、并发控制、失败修复；
  - 资产图批量生成 `generateShuihuoAssetImagesWithRepair`（同文件 3256 行起），最多 5 路并发；
  - 漫画页生成 `comicPageGenerator.generatePage`（[batch_factory_comic_pages.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/httpapi/batch_factory_comic_pages.go#L826)）。
- **复用程度**：**半复用**。生成逻辑完整，但强绑 `batchfactoryv11.Batch / Book / BookAsset` 和“水货”设置，输入是书/资产，不是漫剧镜头。
- **缺口**：
  1. 没有“镜头 → 图片任务”的数据模型；
  2. 没有把 `video_desc` 编译成图片提示词的函数（洛水有 `image_prompt` 字段）；
  3. 没有参考图绑定（角色/场景/道具 → 资产图）；
  4. 没有按镜头记录成功/失败/重试。
- **要新写什么**：
  - 抽一个 `MediaImageService`，输入是“项目 + 分镜镜头 + 资产引用 + 画风 + 比例”，输出是素材地址；
  - 新增 `screenplay_media_jobs`（kind=image, shot_id, status, provider, attempts, artifact_id, error）；
  - 新增 `screenplay_artifacts`（项目、类型、存储地址、mime、宽高、时长、校验值）；
  - 前端：每个镜头组一个“生成/重试/预览”按钮 + 批量按钮。
- **依赖**：图片模型必须在设置里配置可用；部分模型有内容审核，需要重试策略。

#### ② 出视频

- **一句话**：用首帧图 + 视频描述 + 时长，生成一段 5–15 秒的视频。
- **洛水怎么做**：分镜页签内的「视频」子页签（偏移 14963922），支持「批量生视频」（偏移 14685822）；桥命令 `batch_generate_videos / generate_single_video / add_video_task`（偏移 14686374、14686589、14686472）；引擎包括即梦画布、小云雀、可灵、Vidu、SD、Seedance（偏移 2708188、2701953 等）。
- **V88 现成能力**：
  - 视频 provider 常量：`personal_api / doubao_local_executor / autodl_comfyui / yfai_seedance / yfai`（[video_provider.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/batchfactoryv11/video_provider.go#L11-L18)）；
  - MiniMax H3 图+音→视频适配器（[autodl_h3_video_adapter.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/batchfactoryv11/autodl_h3_video_adapter.go#L16-L29)），支持参考图、两步轮询；
  - 通用生产适配器接口 `ProductionAdapter`（[production.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/batchfactoryv11/production.go#L125)）。
- **复用程度**：**半复用**。适配器和轮询都在，但入口是“书 → 生产批次 → 提交”，不是“镜头 → 视频任务”。
- **缺口**：
  1. 没有镜头级视频任务；
  2. 没有“首帧图/参考图”与镜头的绑定；
  3. 没有“生成失败只重试该镜头”；
  4. 没有把视频片段回写到分镜。
- **要新写什么**：
  - `MediaVideoService`：输入镜头 + 首帧图 + `video_desc` + 时长 + provider，输出片段；
  - 任务表复用 `screenplay_media_jobs`（kind=video）；
  - 前端：每个镜头组的视频状态、预览、重试；批量“生成全部未完成”。
- **依赖**：视频 provider 的 key/本机执行器；不同 provider 的时长/比例限制不同，需要在提交前校验。

#### ③ 配音

- **一句话**：把每个角色每句台词，用指定音色读出来。
- **洛水怎么做**：分镜页签内的「配音」子页签（偏移 14971056），支持「批量配音」（偏移 14688875）；分镜数据里有 `voices[]`（`voice_actor / emotion / line`）和 `voice_text`（偏移 8090144、19677700）；桥命令 `batch_generate_narration_audio / tts_batch_start / update_storyboard_voice`（偏移 14689544、16758878、14859031）。**注意：洛水自己的“配音设置”弹窗仍写着“配音功能开发中...”**（偏移 14868497），所以不要把它当完整标杆。
- **V88 现成能力**：
  - 通用 TTS 接口 `POST /api/tts`，输入 `input/voice/speed/pitch/style`，返回音频字节，60 秒超时，32MB 上限（[tts.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/httpapi/tts.go#L55-L138)）；
  - AI-CUT 项目内 TTS：`POST /api/ai-cut/projects/{id}/tts`，单条最多 5000 字，落到项目素材库（[aicut_tts.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/httpapi/aicut_tts.go#L39-L67)）。
- **复用程度**：**高复用（单条）**。接口现成，能直接“文本 → 音频”。
- **缺口**：
  1. `StoryboardShot` 没有台词字段，只有 `video_desc`；需要从 `video_desc` 里解析台词，非常脆弱；
  2. 没有“角色 → 音色”的稳定映射（资产里的 `voice` 只是自由文本）；
  3. 没有批量、并发、重试、时长测量；
  4. 没有把音频写进素材库并与镜头绑定。
- **要新写什么**：
  - 分镜镜头新增 `voices JSON`（角色、情绪、台词）和 `voice_ref`；
  - `MediaAudioService`：按镜头/台词调用 TTS，测量时长，落素材；
  - 任务表 `screenplay_media_jobs`（kind=audio）；
  - 前端：逐条试听、批量配音、音色选择。
- **依赖**：TTS 服务可用；长文本要按句拆分，避免 60 秒超时。

#### ④ 上字幕

- **一句话**：把配音的时间轴变成字幕，或者把台词按时间贴到画面上。
- **洛水怎么做**：「生成字幕」（偏移 14888401），桥命令 `generate_combined_subtitle`、`process_subtitle_alignment_async`；有 ASR 识别 + 与原文对轴。
- **V88 现成能力**：
  - AI-CUT 有 ASR 服务：`OpenAICompatibleASRProvider.Transcribe`（[asr.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/aicut/asr.go#L84)），`ASRService` 能把音频转成 `SRTCue` 并写入时间线（[asr_service.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/aicut/asr_service.go#L48)）；
  - 有字幕编辑能力（`replaceSubtitleText`、`editPlanAddSubtitle`）。
- **复用程度**：**低到中复用**。ASR 能出时间轴，但“把识别结果和原台词对齐”没有现成实现；漫剧更需要“按台词生成字幕”，而不是“识别现场音”。
- **缺口**：
  1. 没有“台词 → 字幕时间轴”的直接通道；
  2. 没有字幕样式/断句规则；
  3. 没有 SRT/ASS 导出到成片。
- **要新写什么**：
  - 优先方案：TTS 时记录每句音频时长，按镜头顺序累加，直接生成 SRT/ASS（不依赖 ASR）；
  - 备选方案：ASR + 文本相似度对齐；
  - 任务表 `screenplay_media_jobs`（kind=subtitle）；前端字幕预览/微调。
- **依赖**：如果走 ASR，需要 ASR 模型；如果走 TTS 时长，只需要 TTS。

#### ⑤ 合音频

- **一句话**：把所有镜头的配音按顺序拼成一条完整音轨，该停的地方停、该留气口的地方留。
- **洛水怎么做**：「合并音频（含气口处理）」（偏移 14898152），桥命令 `merge_subtitle_audio`。
- **V88 现成能力**：
  - `FFmpegRunner.ConcatAudioFiles`（[ffmpeg.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/mergeworker/ffmpeg.go#L219)）；
  - 批量工厂的 `audio` 阶段已经会逐句 TTS 后拼接（[batch_factory_automation.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/httpapi/batch_factory_automation.go#L2717)）。
- **复用程度**：**高复用**。ffmpeg 拼接逻辑现成。
- **缺口**：
  1. 没有“按镜头顺序 + 镜头间静音”的编排；
  2. 没有 BGM 混音/压低；
  3. 没有音频总时长与视频总时长对齐。
- **要新写什么**：
  - `AudioComposer`：输入按镜头排序的音频 + 每镜头目标时长，输出一条音轨；
  - 任务表 `screenplay_media_jobs`（kind=audio_merge）。
- **依赖**：本机 ffmpeg（已有）。

#### ⑥ 合成片

- **一句话**：把多段视频按顺序拼成一条成片，换上合并后的音轨，统一画面规格。
- **洛水怎么做**：「合并成片」（偏移 2698240），桥命令 `merge_storyboards / render_timeline_video`（偏移 26352271、22431712）；支持超长视频分组（100/200/250/300 秒）、片段重拍、相邻分镜合并（最长 30 秒）。
- **V88 现成能力**：
  - `FFmpegRunner.Merge` / `MergeWithAspect` / `MergeWithAudio`（[ffmpeg.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/mergeworker/ffmpeg.go#L132-L214)）；
  - 合并 worker 与对象存储 `TOSObjectStore.PutMerged`（[object_store.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/mergeworker/object_store.go#L88)）；
  - 批量工厂 `merge` 阶段已经会提交合并任务（[batch_factory_automation.go](file:///f:/脚本测试/一战晟铭-v88/backend/internal/httpapi/batch_factory_automation.go#L3679-L3692)）。
- **复用程度**：**高复用**。ffmpeg 合并、音轨替换、对象存储都在。
- **缺口**：
  1. 没有漫剧镜头 → 合并清单的组装；
  2. 没有“按集/按平台时长”分组；
  3. 没有封面、字幕烧录、片头片尾；
  4. 没有成片回写与预览。
- **要新写什么**：
  - `FilmComposer`：输入镜头片段顺序 + 音轨 + 字幕 + 分辨率/帧率，输出成片；
  - 任务表 `screenplay_media_jobs`（kind=film）；
  - 前端成片预览/下载。
- **依赖**：ffmpeg + 对象存储（已有）。

### 7.3 复用程度矩阵

| 环节 | 洛水能力 | V88 现成 | 复用程度 | 主要缺口 | 是否要新后端 |
|---|---|---|---|---|---|
| 出图 | 批量生图 + 参考图 | `generateShuihuoImageArtifact` | 半复用 | 镜头任务模型、提示词编译、资产参考图 | 是 |
| 出视频 | 批量生视频 + 多引擎 | `ProductionAdapter` + 5 个 provider | 半复用 | 镜头任务、首帧绑定、轮询回写 | 是 |
| 配音 | 批量配音 + 音色 | `/api/tts`、AI-CUT TTS | 高复用（单条） | 台词字段、音色映射、批量/重试/测量 | 是（服务层） |
| 字幕 | ASR + 原文对轴 | AI-CUT ASR + 字幕编辑 | 低到中 | 台词对齐、SRT/ASS 导出 | 是 |
| 合音频 | 气口处理 | `ConcatAudioFiles` | 高 | 按镜头编排、BGM、时长对齐 | 少量 |
| 合成片 | 合并/重拍/分组/剪映导出 | `Merge*` + 对象存储 | 高 | 清单组装、分组、字幕烧录、封面 | 少量 |

### 7.4 最小可行顺序（建议）

1. **M1：先让“状态”真实**——任务表 + 每镜头状态 + 预检；不生成任何媒体。这样用户能看到“缺什么”，也方便后面逐环接。
2. **M2：接配音**——因为 `/api/tts` 最现成，且能反过来验证“台词字段”设计是否正确。先做单镜头试听，再做批量。
3. **M3：接合音频 + 合成片**——用已有 ffmpeg，把“已有视频片段 + 已有配音”合成一条成片；此时还不要求自动出图/出视频。
4. **M4：接出图**——用 `generateShuihuoImageArtifact` 抽服务，给每个镜头出首帧。
5. **M5：接出视频**——最后接，因为 provider 差异最大、最贵、最容易失败。

> 这个顺序的好处：每一步都能独立验收，且前两步不依赖图片/视频模型，不会一上来就烧额度。
