# 插件功能验收标准（V88）

本文件把「每个插件功能按四步验收」固化为项目规约。任何插件（含文字工具、本地工具、草稿工具、图片/视频工作台）在标记「可用」前，必须按本文件产出证据。

适用范围：`frontend/src/user/pages/pluginCatalog.js` 中的全部条目，以及后续新增插件。

---

## 1. 四步法

### 第一步：逆向取证

必须逐条给出，不能写「已确认」：

| 项目 | 要求 |
|---|---|
| 入口 | 路由、按钮、事件名；给出文件 + 行号 |
| 调用链 | 前端组件 → API 封装 → 后端 handler → 服务/工具层 → 外部通道（模型/存储/本地桥） |
| 数据变化 | 写哪份存储（MySQL / localStorage / 草稿时间轴 / React state）、哪个键、写入前后的值 |
| 文件与网络请求 | URL、方法、请求体字段、响应字段、超时、大小限制 |
| 关键函数 | 函数名 + 文件 + 行号 + 输入输出 |

证据格式统一为 `文件路径:行号`；洛水侧证据必须能指到 bundle 行号或截图文件名。

### 第二步：五种场景实测

| 场景 | 必测内容 |
|---|---|
| 正常输入 | 完整必填项，记录实际产出与界面状态 |
| 空值 | 全空 / 只有空格 / 只填一半必填项 |
| 重复操作 | 连点两次提交、重复添加、重复保存 |
| 错误操作 | 格式错、地址错、Key 错、超长、特殊字符 |
| 取消操作 | 中途关弹窗、切换页面、取消请求 |

每条记录实际发生什么：有无脏数据、有无重复记录、有无卡住。
**测不了就写「未验证」并写原因**，禁止写「应该没问题」。

### 第三步：转成需求规格

一条功能一节，四段式，必须能照着判「做没做到」：

- **输入**：字段、类型、必填、默认值、取值范围。
- **输出**：结果形态、存放位置、成功后的界面状态。
- **边界**：空值、超长、重复、并发、取消。
- **失败提示**：哪种失败、文案是什么、能否重试、会不会留下半成品。

### 第四步：实现与自检

按规格实现；实现后按同一套规格逐条自检，每条结论对应到具体文件与行号。
自检结果只能是：`通过` / `不通过（差在哪）` / `未验证（原因）`。

## 2. 状态词表（全项目统一）

| 状态 | 含义 |
|---|---|
| 已验证 | 有可复现的测试或运行时证据（贴命令与结果） |
| 部分验证 | 逻辑层已验证，界面/模型层未验证，必须写清哪一段没测 |
| 未验证 | 没有测过；必须写原因（构建冻结、缺少凭证、需要桌面执行器等） |
| 不可行 | 依赖洛水桌面桥或本机资源，V88 当前链路无法提供；必须在界面标注「未接入」 |

「洛水有真实界面」与「洛水只是桌面占位、点开无界面」必须逐条标注：
前者可照抄布局；后者只能按功能链路推导，并在结论里写「推导」。

## 3. 每批交付物

1. 规格文档：`docs/acceptance/<批次>-<范围>-<日期>.md`，一条功能一节。
2. 实现：源码改动（含测试）。
3. 五场景实测记录：命令、输入、实际输出、结论。
4. 与洛水对照：照抄项 / 推导项 / 差异项，附 bundle 行号或截图文件名。

批次文档末尾必须有「未验证清单」与「下一批入口」。

## 5. 执行约束

- 不 commit、不部署、不重启 4001（需要重启先问）。
- 不消耗额度跑真实生成；需要模型的场景用本地 mock。
- 构建冻结期间禁止 `npm run build`、禁止修改 `frontend/dist`；此时界面层只能标「未验证」。
- 源码优先：不得用编译产物覆盖源码实现。
